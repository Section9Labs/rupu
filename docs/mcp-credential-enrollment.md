# Host-owned MCP bearer credentials v1

This feature extends the separate trusted-host MCP registry. It does not install a provider account, inspect provider credentials, or use RUPU_AUTH_FILE. The rupu-auth owner stores MCP-only bindings in `<trusted-global-root>/mcp-credentials.json`, with its private sidecar lock. The path is determined by the existing connected host global root, never supplied by an HTTP client. This is a private plaintext file, not an encrypted vault or an OS keychain. It uses rupu-providers private-file creation, fsync/atomic replacement, mode0600 checks and bounded SidecarLock; a process mutex also excludes same-process writers on process-scoped flock implementations. Static non-file/symlink entries are refused; this is not descriptor-anchored defense against malicious races inside the trusted host root.

`use_host_store` first selects the mechanism in the registry and creates a canonical ULID binding generation. Token enrollment is a separate operation; a configured mechanism is not proof a token exists or authenticates. Existing dedicated RUPU_MCP_* environment references remain compatible. A binding contains exact server ID, canonical configured endpoint and random generation. Endpoint/mechanism changes and delete/recreate rotate the generation, which participates in frozen session configuration identity. Label/effect changes still affect existing registry fingerprint behavior. Token rotation alone preserves the same endpoint binding; already-connected clients keep their in-memory header until reconnect, not a retroactive revocation guarantee.

All credential routes are operator HTTP only, explicitly excluded from MCP tools. They require an internal request extension inserted by the actual bearer/cookie authentication middleware only after successful verification; token_set or a writable launcher alone is insufficient. Cookie writes retain same-origin protection. Host must be local; mutations additionally require a writable cp serve. Enrollment is not advertised unless a token is configured and the CP is writable. Native token entry must independently require HTTPS or literal loopback HTTP for the CP connection; the backend does not infer TLS from untrusted forwarding headers.

## Contract

- Feature: `mcp.credential_enrollment.v1`.
- `GET /api/mcp/servers/:id/credential?host=local`: `{version:1,host_id:"local",scope:"trusted_host",server_id,registry_revision,binding:{server_id,url,generation},credential:{present,revision},writable}`. Requires the server's host-store mechanism. Initial credential revision is `absent`; later revisions are random lowercase32hex, never a token digest.
- `PUT` the same route: `{operation_id,registry_revision,binding_generation,credential_revision,token}`. IDs are canonical uppercase26-character ULIDs. Token is1–8192 printableASCII bytes excluding whitespace/control. Body limit24KiB. No Debug implementation for token-bearing bodies or storage records.
- `DELETE` the same route: identical fields except no token.
- Mutation success HTTP200: `{version:1,host_id:"local",scope:"trusted_host",receipt:{operation_id,action:"enroll"|"remove",binding,previous_revision,credential_revision,present}}`.
- `GET /api/mcp/credential-operations/:id?host=local` returns that exact durable receipt.404 means no receipt found, not proof a timed-out mutation failed.
- Errors include human `error` plus fixed `code`/`mutation_outcome`: stale registry/binding/credential revision409 = `precondition_failed`/`not_applied`; reused operationID409 = `operation_id_used`/`unknown`; known request rejections = `request_rejected`/`not_applied`; storage/write/task failures = `storage_unavailable`/`unknown`. Capacity507 is a known prewrite rejection. Outer auth middleware can reject with its established401/403 envelope before the credential handler. No error contains request bodies or secret-store contents.

Registry CAS is held across the credential transaction (lock order registry→credential). Token/tombstone, random revision and nonsecret receipt commit in one private atomic document replacement. No repeated operation is applied; inspect its receipt instead. Readers cannot observe a successful token update without the matching receipt in that document. A filesystem/directory-sync failure after replacement is uncertain; read the operation, do not automatically repeat the write. This does not claim atomicity across the registry and secret store: configuring a mechanism and enrolling its token are intentionally separate writes.

## Orphan lifecycle

Clearing/changing a registry mechanism or deleting a server does not silently erase its old token. That exact old binding becomes orphaned and is unusable by a replacement server generation. `GET /api/mcp/credential-orphans?host=local&offset=0&limit=50` lists metadata for retained tokens only, with version/host/scope/registry_revision/offset/limit/next_offset and rows `{binding,revision,present}`. Limits are1–100 and pages are explicit. `DELETE /api/mcp/credential-orphans/:generation` accepts `{operation_id,registry_revision,binding,credential_revision}` and verifies it is not currently referenced under the registry lock. Removal leaves a nonsecret tombstone and durable receipt; it never removes provider credentials. Current bindings must use their server credential removal route.

The store is bounded to16MiB,4096 binding entries and16384 operation receipts. Capacity is refused before writing; old receipts are never silently evicted. Compaction/retention management is not implemented. A remote host transport, OAuth enrollment/refresh, encrypted-at-rest storage and per-user credential administration roles are outside this v1. The current shared CP token establishes operator authority, not individual attribution.

## Verification scope

Fixture-only tests cover authentication-marker enforcement, local/writable gates, exact binding, random/CAS revision rules, concurrent one-winner writes, response-loss receipt recovery, operation replay refusal, recreation isolation, explicit orphan removal, token redaction, malformed stores, file permissions/symlinks, and MCP resolver refusal without the correct host-store binding. Tests have been written but are not run in the source-authoring branch. No real tokens, environment values or provider auth files were read. Build/tests and actual native capture/connected-server acceptance remain integration work.
