Transcripts

Every agent run rupu executes writes a transcript: an append-only JSON Lines file with one event per line, recording what was sent, what came back, every tool call and what it did. This page is the schema, for anyone who reads transcripts with their own tools.

Where transcripts live

Each agent run writes one file, named after its run id:

<transcripts-dir>/run_<ULID>.jsonl            # an active transcript
<transcripts-dir>/archive/run_<ULID>.jsonl    # after rupu transcript archive
DirectoryUsed when
<project>/.rupu/transcripts/The directory exists in the project the run started in.
~/.rupu/transcripts/ (or $RUPU_HOME/transcripts/)Otherwise.
  • The file name is the run id. run_ plus a 26-character ULID, so names sort by start time. Only run_start and run_complete repeat the id inside the file.
  • A workflow writes one transcript per agent run, in the same directory: each linear step, each for_each / parallel / panel unit, and each sub-agent started with dispatch_agent. The workflow run’s own records (run.json, step_results.jsonl, events.jsonl) live elsewhere and point at each step’s transcript path.
  • Not every .jsonl in the directory is an agent transcript. run: step and action: step logs and per-run netflow ledgers use the same naming with their own shapes. An agent transcript always starts with run_start; a file with no run_start anywhere is one of the others, and rupu’s readers skip it.

File format

One JSON object per line, UTF-8, newline-terminated. Every line has the same envelope:

{"type": "<event>", "data": { … }}
  • type is the event name in snake_case; so are all field names.
  • Optional fields are omitted, not null, when they have no value, and boolean flags that default to false are usually omitted when false. Treat a missing key as its default.
  • Files are only ever appended to. Several writers (the agent loop, the tool_audit hook, the netflow sink) append to one file, each line whole.

Schema versions

run_start.schema says which writer produced the file. Current rupu writes 2; a transcript with no schema key is version 1.

VersionWhat it records
1 (no key)The conversation as text. Reasoning, if any, is a plain thinking string on assistant_message, with no provider payload.
2Enough to rebuild the exact conversation sent to the provider: the effective system_prompt on run_start, the user_message, each reasoning block as a thinking event with the provider’s byte-exact raw block, any seed the run started from, and every compaction.

Fields and events have been added within version 2 since it shipped (outcomes, recovery, customer, codenames, cache-write tokens). A reader should accept a missing optional key and an unknown event.

Reading rules

  • No run_complete means the run was killed or crashed (or is still going). Treat it as aborted, the status rupu transcript list gives it. Everything before the end is still valid.
  • A truncated last line is a write cut off by a crash. Skip it.
  • Empty lines: skip them.
  • A malformed line mid-file is an error for that line only; keep reading the rest.
  • An unknown type is not an error. See Unknown events.

Event order

Within one file:

run_start
seed?                     # a run seeded from earlier history (continue, session, resume)
user_message?
( turn_start
    usage                 # one per provider call; a compaction call adds one with purpose
    outcome?              # a non-normal reply, ahead of the turn's content
    ( thinking_delta* thinking | assistant_delta* assistant_message | assistant_block )*
    ( tool_call  tool_result  file_edit?  command_run?  action_emitted?  tool_audit? )*
  turn_end
  recovery*               # steps taken for the turn's outcome
  notice* compaction? )*
net_flow*                 # interleaved anywhere, as connections close
run_complete

Reasoning, text, tool calls and other blocks appear in the order the model produced them. A notice can appear wherever the runtime intervened; a fallback hop writes a model_limits notice just before its fell_back recovery. A note sent back to the model mid-run (for example after an interruption) is a user_message.

Event reference

Fields marked opt are omitted when empty.

run_start

The first line of every agent transcript.

FieldTypeMeaning
run_idstringSame as the file name without .jsonl.
workspace_idstringThe workspace (project) record, ws_….
agentstringAgent name from its frontmatter.
provider / modelstringWhat the run was configured to use. A fallback hop shows up later, not here.
started_atRFC 3339Start time, UTC.
modeask | bypass | readonlyThe permission mode.
schemainteger, opt2 today; absent on version 1.
system_promptstring, optThe system prompt actually sent, after rupu appended its own sections (coverage catalog, run target).
codenamestring, optThe run’s human codename, e.g. amber-delta/kestrel#2.
customerstring | null, optThe customer slug. null means recorded as no customer; no key means the transcript predates customers.
 
{"type":"run_start","data":{"run_id":"run_01JB7Q2M4X8T6V0K3N5R9C1D2E","workspace_id":"ws_01JB7PZ0A1B2C3D4E5F6G7H8J9","agent":"code-reviewer","provider":"anthropic","model":"claude-sonnet-4-6","started_at":"2026-10-07T09:14:03Z","mode":"readonly","schema":2,"codename":"amber-delta/kestrel"}}

run_complete

The last line of a run that ended. Its absence means the run never finished.

FieldTypeMeaning
run_idstringSame as run_start.
statusok | error | abortedHow it ended.
total_tokensintegerTokens across all turns.
duration_msintegerWall-clock duration.
errorstring, optThe error, when status is error.
outcomeOutcomeRecord, optThe outcome the run failed on, when it failed because recovery ran out.

turn_start, turn_end and usage

EventFields
turn_startturn_idx — zero-based turn counter.
turn_endturn_idx; opt tokens_in, tokens_out; opt stop_reason (the provider’s own stop value, e.g. end_turn); opt response_id; opt stop, a StopRecord: reason (normalized: end_turn, max_tokens, refusal, pause_turn, …), wire (provider name, raw value, extras), opt refusal, opt served_by (the model that answered when a server-side fallback served the turn); opt discarded: true when the turn’s content was thrown away (a refused, blocked or retried reply) — it was never sent back to the model.
usageOne per provider call: provider, model (requested), opt served_model (if the provider served another), input_tokens, output_tokens (billable, reasoning included), cached_tokens (cache reads, part of input_tokens), opt cache_write_tokens (Anthropic only), opt purpose: "compaction" for the context-compaction summarizer — real spend, but not an agent turn.
 
{"type":"usage","data":{"provider":"anthropic","model":"claude-sonnet-4-6","input_tokens":18240,"output_tokens":612,"cached_tokens":16384}}
{"type":"turn_end","data":{"turn_idx":3,"tokens_in":18240,"tokens_out":612,"stop_reason":"tool_use"}}

Conversation events

EventFieldsNotes
user_messagecontentThe prompt this run added. Absent on a run that only continues a seed.
assistant_messagecontent; opt thinkingOne complete text block. thinking is the version 1 reasoning string.
assistant_deltacontentA streamed chunk ahead of its assistant_message. Ignore it unless you’re rendering live.
thinkingopt text, provider, model, rawOne reasoning block, in its real position in the reply. raw is the provider’s exact block, signatures included, kept for replay; never display it. No text means the reasoning was redacted.
thinking_deltacontentA streamed reasoning chunk; the thinking event has the whole block.
assistant_blockblock; opt abandonedA reply block with no event of its own: a server-side fallback boundary (from_model → to_model) or an unknown block with the provider’s raw payload. abandoned: true marks a block the API discarded at a mid-reply fallback.
seedmessage_count, sha256; opt source_transcript or messagesThe history this run started from, stored once: either a reference to the transcript it was rebuilt from, or the messages inline. sha256 covers the seed either way, so a reader can verify a reference chain.
compactionseq, summarized_messages, backup_path, messagesContext compaction rewrote the conversation. messages is the whole conversation afterwards, which the following turns were built from.

Tool events

EventFieldsNotes
tool_callcall_id, tool, inputThe model asked for a tool. input is the JSON it sent.
tool_resultcall_id, output, opt error, duration_ms, opt structuredPairs with its tool_call by call_id. structured is a machine-readable payload some tools add, e.g. ast_grep’s match ranges and metavariable bindings.
file_editpath, kind (create | modify | delete), diffWritten alongside a write_file / edit_file result, so you can index edits without parsing tool inputs.
command_runargv, cwd, exit_code, stdout_bytes, stderr_bytesWritten alongside a bash result.
action_emittedkind, payload, allowed, applied, opt reasonA workflow action: step’s connector call: kind is the catalog tool (issues.comment), payload its rendered with:. applied is false only when the call was refused before reaching the connector. Old transcripts may carry free-form verbs here that no longer exist.
tool_audittool, declared, granted, blocked, restrictedOne per connector (MCP catalog) call in a workflow step, by an agent or an action: node; never for built-ins. See below.

tool_audit is the audit trail for a step’s actions: narrowing:

FieldTrue when
restrictedThe step declared a non-empty actions: list.
declaredThat list names this tool. Always false on an unrestricted step, which isn’t a violation.
grantedThe agent’s tools: covers the tool, before narrowing (wildcards expanded). Always true for an action: node.
blockedThe call was denied: narrowed out of the step, or refused by the permission mode.
 
# an action: step that commented on an issue
{"type":"action_emitted","data":{"kind":"issues.comment","payload":{"project":"acme/widgets","number":88,"body":"Triage done."},"allowed":true,"applied":true}}
{"type":"tool_audit","data":{"tool":"issues.comment","declared":false,"granted":true,"blocked":false,"restricted":false}}

outcome and recovery

When a reply isn’t a normal one, or the provider returns an error, rupu classifies it and records what it did about it. The classes and the recovery ladder are explained in Recovery & reliability.

outcome has turn_idx and an outcome object (an OutcomeRecord; the same shape as run_complete.outcome):

FieldTypeMeaning
idstringUnique in the run (oc_1, oc_2, …). Recovery events point back to it.
classstringpause_turn, max_tokens, context_window_exceeded, refusal, safety, malformed_tool_call, incomplete, empty_reply, unrecognized_stop, unreported_stop or provider_error. A string, so a class added later still parses.
severityinfo | warning | error
titlestringOne line, e.g. refused · cyber.
detailstring, optLonger text: the refusal’s explanation, the cut-off tool call, the provider’s error message.
error_classstring, optFor provider_error: rate_limited, overloaded, server, timeout, context_overflow, quota, not_found, policy, auth, permission, invalid_request, too_large or unrecognized.
wireobject, optThe provider’s own stop value or error body, verbatim.

recovery is one step taken for an outcome:

FieldTypeMeaning
outcome_idstringThe outcome it answers.
runginteger0 in place, 1 fallback on the same provider, 2 fallback on another provider, 3 nothing left: the run fails.
actionstringcontinued, retried, compacted, fell_back, served_by_fallback, skipped or failed (asked and parked are reserved). Treat an action you don’t know as other.
attempt / budgetinteger, optWhich rung-0 attempt this is, out of how many.
provider / modelstring, optThe fallback, for fell_back, served_by_fallback and skipped.
reasonstring, optWhy: the hint on failed, the build error on skipped.
merge_into_previousbool, optThe next turn’s reply continues the previous assistant message (a pause_turn).
continues_outputbool, optThe next turn’s text continues this turn’s answer (after truncation), so the final answer joins across the boundary.
 
{"type":"outcome","data":{"turn_idx":4,"outcome":{"id":"oc_1","class":"provider_error","severity":"warning","title":"overloaded","error_class":"overloaded"}}}
{"type":"recovery","data":{"outcome_id":"oc_1","rung":0,"action":"retried","attempt":1,"budget":3}}

notice

A runtime intervention worth showing that isn’t part of the conversation: kind and a human-readable message. Kinds written today: model_limits (the run’s context and output limits and where each came from), model_limits_clamped, context_trim, provider_retry and server_side_fallback_disabled. Expect new kinds; render unknown ones by their message.

net_flow

One outbound network connection the run made: {"flow": <FlowRecord>}, with the host, port, scheme, method and path, status and outcome, bytes in and out, timing, and a fidelity that says how much of it rupu actually observed (rupu’s own HTTP calls are seen in full; connections a bash command opens are seen from the OS socket table). The record is described on the Netflow page.

gate_requested

Defined (gate_id, prompt, opt decision, opt decided_by) but not written by current rupu: workflow approval gates are recorded on the workflow run, not in agent transcripts.

Unknown events

A line whose type a reader doesn’t know is not corruption. rupu reads it as an unknown event that keeps the raw type and data, and writes it back unchanged, so a transcript from a newer rupu survives being read and copied by an older one. rupu transcript show prints it as unrecognized event · <type> and the control plane shows an “unrecognized event” block. Your own reader should do the same: skip or pass through, never fail.

What is corruption: a line that isn’t a JSON object, has no type, or has a type that isn’t a string.

Working with transcripts

CommandWhat it does
rupu transcript listProject and global transcripts, newest first, with status and tokens. --limit N (default 50), --archived or --all. Supports --format json|csv.
rupu transcript show <run>Render one transcript. <run> is a run id, a unique prefix of one, or a codename. --view focused|compact|full picks the density; --no-pager, --no-color.
rupu transcript archive <run>Move a standalone run’s transcript into archive/.
rupu transcript delete <run> --forceDelete a standalone transcript permanently.
rupu transcript prune --older-than 30dDelete archived transcripts older than the cutoff; --dry-run previews.

For your own tooling, --format jsonl on show prints the parsed events one per line in the schema above, and --format json wraps them in one object ({"kind": "transcript_show", "version": 1, "item": {"run_id", "path", "events"}}). Or read the file directly:

# every bash command a run executed, with its exit code
jq -c 'select(.type=="command_run") | [.data.exit_code, (.data.argv|join(" "))]' \
  .rupu/transcripts/run_01JB7Q2M4X8T6V0K3N5R9C1D2E.jsonl

# total spend per model across a run, cache reads included
jq -s 'map(select(.type=="usage").data) | group_by(.model)
       | map({model: .[0].model, input: (map(.input_tokens)|add), output: (map(.output_tokens)|add)})' \
  .rupu/transcripts/run_01JB7Q2M4X8T6V0K3N5R9C1D2E.jsonl

# connector calls a narrowed step blocked
jq -c 'select(.type=="tool_audit" and .data.blocked)' .rupu/transcripts/*.jsonl

Replay

A version 2 transcript is enough to rebuild the exact conversation the provider saw, and rupu does exactly that when it continues a run: rupu run --continue <run-id>, rupu workflow resume picking up an interrupted step, and a session’s next turn. The rules, if you want to rebuild one yourself:

  • Start from the seed, if any. A source_transcript seed means “rebuild that transcript first”; the chain can be several deep, and its sha256 must match what you rebuilt.
  • Add the user_message. Per turn, fold thinking (its raw block), assistant_message, tool_call and assistant_block events, in file order, into one assistant message, skipping abandoned blocks; then the turn’s tool_results become the next user message.
  • Drop a turn with no turn_end (it was in flight) and a turn whose turn_end is discarded. A recovery with merge_into_previous joins the next turn’s reply onto the previous assistant message.
  • A compaction replaces everything so far with its messages.

A version 1 transcript rebuilds without reasoning blocks, since it never kept the provider’s payload. Deltas, usage, notice, outcome, tool_audit, net_flow and unknown events don’t affect the conversation.
