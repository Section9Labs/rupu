Engagement profiles

An engagement profile tells rupu what kind of thing an engagement is about — source code, a binary, a network, a web application, a cloud account, a threat model — and therefore what a complete finding about it looks like.

Concepts

A profile is a small TOML file. It declares the asset kinds that exist in its domain, the coordinates that pin each one down, a completeness checklist that every finding must pass, and a depth ladder that records how far each asset has been examined. rupu ships 15 profiles. You can override any of them, or add your own by writing a TOML file — no Rust needed.

  • Asset. A finding is always about something: a file, a function at an address, a service on a host, a route, a cloud resource. That thing is an asset. It has a kind, a locator and, optionally, a depth.
  • Kind. Every kind belongs to a profile and carries its namespace: network:service, web:route, binary:function. Kinds can form a hierarchy within their profile (a service sits under a host).
  • Routing. When a finding names an asset, its kind’s namespace picks the profile that owns it. That profile, and only that profile, judges the finding.
  • Validation. The owning profile’s required completeness checks run against the finding’s report and the asset’s locator. A finding that fails is rejected, and the error lists each unmet check, so the agent can fix it and record it again.
  • Depth. Each profile has a depth ladder, such as discovered → enumerated → tested → exploited. It records how deeply each asset was examined, separately from any findings about it.
Not a sandbox. A profile governs how findings are typed, routed and validated. It doesn’t run, gate or scope tools, and it doesn’t limit what an agent can reach. Agents examine binaries, hosts and services with bash and whatever tooling they like; rupu records and validates the findings that result, not the traffic.

Coordinates

A locator is the set of typed coordinates that pins an asset down. The core knows exactly 13 coordinate types, and every profile builds on them. Each is written as {"t": <tag>, "v": <value>}. A locator can be empty — a threat-model component has no coordinates at all.

Selecting profiles

rupu run --engagement-profile binary  firmware-re "reverse ./dist/updater.bin"
rupu run --engagement-profile network recon       "map 10.20.0.0/24"
rupu run --engagement-profile network,web assessor "..."   # two profiles
rupu run --engagement-profiles pentest assessor    "..."   # a composite
rupu workflow run edge-sweep --engagement-profile network

Every built-in profile also declares a [bundle]: the agents and workflows an engagement of that kind typically uses. A bundle never grants tools. The stock security fleet is built from these bundles, and rupu’s own tests keep the two in lockstep.

Composites and routing

A composite is a profile with an includes list. Selecting one is shorthand for selecting its members, and each member stays its own routing target — the members are not merged. During a pentest run, a network:service finding is judged by network’s checks and a web:route finding by web’s. mobile adds its own root kind, mobile:package, alongside binary and web. includes is transitive; an include cycle, or an include of a profile that doesn’t exist, is a load error.

The stock security fleet

A profile says what a complete finding looks like; it doesn’t ship anyone to find them. The stock fleet does: 18 generic security-assessment agents and 3 workflows, one set for every built-in bundle. Install it once and every engagement, in any project, can draw on it.

rupu fleet list                    # what the fleet ships
rupu fleet install                 # into ~/.rupu (or $RUPU_HOME)
rupu fleet install --project       # into this project's .rupu/ instead
rupu fleet install --force         # re-seed files you've edited

The fleet is plain files: agents/<name>.md and workflows/<id>.yaml, written exactly where rupu’s loaders look. A file that already exists is kept, so your edits survive a reinstall; each file is reported as CREATED, SKIPPED or OVERWROTE. --force overwrites them with the shipped versions. --project needs a .rupu/ (run rupu init first), and a project copy shadows the global one, as for any agent or workflow.

  • Specialists each do one job inside the authorized scope they’re given. Discovery agents (recon, crawler) map and asset_mark what they find but don’t test; analysts and testers verify before they report_finding, pinned to the asset with the evidence and classification their profile’s checks require; exploit-verifier independently confirms or refutes claimed exposures.   • The workflows chain the same agents for a fixed run: network-assessment is recon → analyze → verify, web-assessment is crawl → test, and api-assessment is a single assess step. Each takes one required input, scope.

Run a workflow under its profile so the asset and findings tools are active:

rupu fleet install
rupu workflow run web-assessment --engagement-profile web \
  --input scope="https://staging.example.test (exclude /admin/billing)"

Or hand the whole pool to the lead in an agentiflow:

# .rupu/agentiflows/lab-sweep.yaml (excerpt)
lead: assessment-lead
engagement_profiles: [network]
pool:
  agents: [assessment-lead, recon, service-analyst, exploit-verifier]
  workflows: [network-assessment]
Bundles and the fleet stay in step. A test fails rupu’s build if any built-in bundle names an agent or workflow the fleet doesn’t ship, or if the fleet ships one no bundle names. A bundle in your own profile isn’t checked against anything, and rupu doesn’t install or select a bundle’s members when you pick the profile — you still name the agent or workflow you run.

Recording assets

Two tools write assets, both to the target’s asset ledger, .rupu/coverage/<target>/assets.jsonl, next to findings.jsonl.

report_finding with an asset

{
  "scope": "edge-sweep",
  "report": { /* a complete finding report */ },
  "asset": {
    "kind": "network:service",
    "coordinates": [
      { "t": "host", "v": "198.51.100.20" },
      { "t": "port", "v": { "number": 8443, "proto": "tcp" } }
    ],
    "label": "198.51.100.20:8443 admin console"
  }
}

When an engagement is active, rupu:

  1. Routes the finding by its namespaced kind. If no active profile owns the kind, the call fails, and the error names the active set.
  2. Checks completeness. Every required check of the owning profile is evaluated under the full finding profile. If any check fails, the finding is rejected with the labels of the failing checks. Under summary there’s no report to evaluate, so this step is skipped.
  3. Stamps the asset into assets.jsonl and the run’s coverage stream, so a coordinator collecting a remote unit receives it. The new line keeps the asset’s existing depth, parent, attributes and label, unless the call supplies a new label.

The finding record itself does not store an asset id. When no engagement is active, asset is ignored. When an engagement is active but the finding has no asset, it records on the plain path without a completeness check. The MCP findings.record tool doesn’t accept asset yet, and rupu findings import records no asset.

asset_mark

{ "kind": "web:route",
  "coordinates": [ { "t": "url", "v": "https://shop.example.test" },
                   { "t": "http_route", "v": { "method": "POST", "path": "/cart/apply" } } ],
  "depth": "tested" }

depth must be a rung of the owning profile’s ladder; any other value is an error that lists the ladder. Depth only moves forward: if an asset is already at exploited, marking it tested leaves it at exploited, and the tool returns the rung that ends up recorded (effective_depth). The engine offers asset_mark and report_finding to every agent in an engagement run, whatever the agent’s tools: list says. Without an active engagement, asset_mark doesn’t exist.

The ledger and its views

assets.jsonl only ever gets appended to, one full asset per line (id, kind, parent, locator, label, depth, attributes). When the file is read, the last line for each id wins. An asset’s id is <kind>:<16 hex>, derived from the kind plus the sorted locator, so the same host and port always map to the same asset, across reruns too. The profile’s label template is declarative and isn’t rendered: an asset’s label is whatever the caller passed, or else its kind.

Remote units’ asset lines arrive through the coverage stream and are merged into the coordinator. The control plane’s Security → Assets page lists every asset from every registered workspace, and an agentiflow’s Assets tab shows the same data for one run (both use GET /api/assets). Agentiflow coverage goals measure this ledger.

Writing a profile

Where profiles live

SourceLocationPrecedence
Built-incompiled into the binarylowest
Global~/.rupu/profiles/*.tomloverrides built-in
Project.rupu/profiles/*.toml in the run’s workspace (for an agentiflow, the directory you launch from)highest

rupu identifies a profile by its id field; the file name doesn’t matter. A later source with the same id replaces the earlier profile completely — nothing is merged — so to change one check of a built-in, copy the whole built-in and edit the copy. Within one directory, files load in name order, and the last one wins. Only *.toml files are read, and a missing directory is fine.

Schema

All keys are strict: an unknown key in any table is a parse error. Put the top-level keys before the first [[asset_kinds]], or TOML assigns them to that kind and the file fails to parse.

KeyTypeMeaning
idstring, requiredProfile id, and the namespace of its kinds (<id>:<kind>)
namestring, requiredHuman-readable name
includesstring listProfiles this one includes (makes it a composite)
evidence_blocksstring listEvidence-block kinds the engagement expects (advisory)
classification_systemsstring listTaxonomies the engagement uses (advisory)
[[asset_kinds]] idstring, requiredBare kind id, namespaced as <profile>:<id>
[[asset_kinds]] parentstringParent kind id in the same profile; omit for a root
[[asset_kinds]] coordinatesstring listCoordinate tags an asset of this kind carries (descriptive)
[[asset_kinds]] labelstring, requiredLabel template such as "{host}:{port}" (descriptive, not rendered)
[[completeness]] id / labelstring, requiredCheck id; the label is shown in the rejection message when the check fails
[[completeness]] requiredbool, default truefalse makes the check informational; it isn’t evaluated
[[completeness]] satisfied_whenpredicate, requiredSee below
[coverage] enumeratesstring listBare kind ids that agentiflow coverage goals count by default
[coverage] depth_ladderstring listOrdered rungs, shallowest first; the only depths asset_mark accepts. The last rung is a coverage goal’s default target.
[bundle] agents / workflows / toolsstring listsThe agents, workflows and tools an engagement of this kind typically uses. Descriptive only: never a grant, and nothing installs or loads them for you

Predicates

PredicateTrue when
{ has_field = "…" }the report field is filled in: root_cause, remediation, impact, description, attack_vector, category (non-blank), replication_steps (non-empty), evidence (any claim or block)
{ has_block_kind = "…" }the report has at least one block of that kind: text, code_slice, diff, table, image, hexdump, disasm, decompile, http_exchange, scan_output, pcap_ref
{ has_classification_system = "…" }a classification uses that system (case-insensitive)
{ locator_has_coordinate = "…" }the asset’s locator has a coordinate with that tag
{ min_severity = "…" }rating.risk_rating is at least Low, Medium, High or Critical (capitalized)
{ all = [ … ] } / { any = [ … ] }every / at least one nested predicate holds

That is the whole predicate grammar. It isn’t meant to grow into a scripting language.

Test with one finding. Loading checks only the TOML structure. A predicate’s field names, block kinds and coordinate tags are first checked when a finding reaches it, so record one real finding against a new profile before you rely on it.

Worked example: an IoT fleet engagement

The profile below is invented for this guide. It covers fleets of embedded devices: a device is found by its address, it exposes services, and each firmware build is identified by its hash. Save it as .rupu/profiles/iot-fleet.toml:

id = "iot-fleet"
name = "IoT device fleet assessment"
evidence_blocks = ["text", "scan_output", "hexdump", "http_exchange", "table"]
classification_systems = ["CWE", "CVE"]

[[asset_kinds]]
id = "device"
coordinates = ["host"]
label = "{host}"

[[asset_kinds]]
id = "service"
parent = "device"
coordinates = ["host", "port"]
label = "{host}:{port}"

[[asset_kinds]]
id = "firmware"
parent = "device"
coordinates = ["host", "sha256"]
label = "{sha256}"

[[completeness]]
id = "pinned"
label = "Pinned to a device service or a firmware build"
satisfied_when = { all = [
  { locator_has_coordinate = "host" },
  { any = [ { locator_has_coordinate = "port" }, { locator_has_coordinate = "sha256" } ] },
] }

[[completeness]]
id = "evidence"
label = "Scan output, hexdump or HTTP exchange attached"
satisfied_when = { any = [
  { has_block_kind = "scan_output" },
  { has_block_kind = "hexdump" },
  { has_block_kind = "http_exchange" },
] }

[[completeness]]
id = "classified"
label = "Classified (CWE or CVE)"
satisfied_when = { any = [ { has_classification_system = "CWE" }, { has_classification_system = "CVE" } ] }

[[completeness]]
id = "has_fix"
label = "Remediation for high-severity issues"
required = false        # informational: not evaluated
satisfied_when = { has_field = "remediation" }

[coverage]
enumerates = ["device", "service", "firmware"]
depth_ladder = ["discovered", "fingerprinted", "tested", "exploited"]
rupu run --engagement-profile iot-fleet fleet-recon "assess the lab segment 192.0.2.0/28"

During the run, the agent might call asset_mark with kind iot-fleet:device, host 192.0.2.7 and depth fingerprinted, then call report_finding with an iot-fleet:service asset pinned by host and port 23/tcp, and a report that has a scan_output block and a CWE classification. If the agent omits the port and the hash, the finding is rejected with Pinned to a device service or a firmware build, and the agent can add the missing coordinates and try again.
