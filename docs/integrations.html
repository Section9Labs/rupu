Integrations

rupu plugs into your source host and your issue tracker so agents can read issues, work in repos, open pull requests, and comment back — across more than one platform at once.

Plug rupu into your stack

Integrations are how rupu reaches out beyond your laptop. Two connector families do the work, and both speak through rupu's single embedded MCP server so agents call the same typed tools regardless of which platform a call resolves to:

  • Source control (SCM) — the RepoConnector. List and read repos, clone working trees, read files by ref, open pull requests / merge requests. Ships for GitHub and GitLab.
  • Issue trackers — the IssueConnector. Fetch and list issues, comment, create, and transition state. Ships for GitHub Issues, GitLab Issues, Jira, and Linear.

Per-platform connectors absorb the vendor quirks — GitLab MR vs GitHub PR vocabulary, nested namespaces, rate-limit headers — so your agent files stay portable. An agent that reads scm.prs.diff and posts scm.prs.comment works against GitHub and GitLab unchanged.

One auth flow. SCM and tracker credentials go through the same rupu auth login path as your model providers, stored in ~/.rupu/auth.json (mode 0600). rupu auth status lists SCM and tracker rows automatically, and you can hold more than one account per platform.

Source control (SCM)

The RepoConnector handles everything repo-shaped. When a run targets a repo or a PR (not a bare issue), rupu clones the repo into a tempdir and runs the agent there; issue targets skip the clone and rely on read tools.

PlatformAPIWhat rupu can do
GitHub REST List / get repos & branches, create branches, read files by ref, list / get PRs, fetch diffs, comment on PRs, open PRs (incl. draft), clone_to local checkout, dispatch a GitHub Actions workflow_dispatch. GitHub Enterprise Server via a base_url on the account.
GitLab REST The same surface, with MR vocabulary translated to scm.prs.*: list / get repos & branches, read files, list / get MRs, fetch diffs, comment, open MRs, clone_to, trigger a CI pipeline against a ref. Nested groups and self-managed instances (base_url on the account) supported.

Run-targets pick a platform by prefix. PRs use #N on GitHub and !N on GitLab (GitLab's MR convention):

# repo working tree / PR / MR / issue
github:owner/repo            # repo
github:owner/repo#42         # PR 42
github:owner/repo/issues/123 # issue 123
gitlab:group/sub/project!7   # MR 7

The rupu repos CLI

List remote repos and manage the local repo registry (which checkout on disk maps to which repo ref):

rupu repos list                       # list repos across configured platforms
rupu repos attach github:owner/repo   # map a local checkout to a repo ref
rupu repos prefer github:owner/repo   # mark a checkout as the preferred path
rupu repos tracked                    # list locally tracked checkouts
rupu repos forget github:owner/repo   # forget a repo or one tracked path

clone_to currently uses the public host's clone URLs, so it refuses an account whose base_url points at a GitHub Enterprise or self-managed GitLab host rather than send that account's token elsewhere. With clone_protocol = "ssh" clones go through your system git and SSH agent instead of an embedded token.

Private repos missing? Your token likely lacks the repo scope, or it is a GitHub App user-to-server token (no OAuth scopes). rupu repos list diagnoses this and tells you whether to re-login with a classic PAT or install the app on the relevant org.

Issue trackers

The IssueConnector family lets agents read and write tracker state. All four trackers work with the issues.* MCP tools (list, get, comment, create, update state); GitHub Issues and GitLab Issues also drive the rupu issues CLI, and Jira and Linear add native trigger sources (polling and webhook — see Triggers). Reading an issue's existing comment thread (issues.comments, oldest-first) is GitHub-only today; the other trackers answer “not supported”.

TrackerAuthWhat rupu reads / writes
GitHub Issues PAT or device-code SSO List, fetch (title, body, state, labels, author), read the comment thread, comment, create, transition open/closed. Full issues.* tools + rupu issues. Plus issue / PR / push event triggers.
GitLab Issues PAT or browser-callback PKCE SSO The same read/write surface except the comment-thread read (#N for issues; MRs use !N). Plus issue / MR / push event triggers.
Jira API key — store as <email>:<api_token> Project-scoped IssueConnector (the issues.* tools, minus the comment-thread read) + native trigger source. Polls jira:<site>/<project> (or jira:<project> with [scm.jira].base_url); normalizes jira.issue.opened / jira.issue.updated and workflow-state transitions.
Linear API key Team-scoped IssueConnector (the issues.* tools, minus the comment-thread read) + native trigger source. Polls linear:<team-id>; normalizes linear.issue.opened / linear.issue.updated and native workflow-state changes.

GitHub Projects (v2) also drives the tracker workflow vocabulary: when an issue-backed project item's Status field changes, rupu maps it into portable issue.* aliases (e.g. issue.entered_workflow_state.ready_for_review). Projects native state mapping is webhook-only today — there is no poll_sources form for Projects yet.

The rupu issues CLI

Auto-detects the target repo from the cwd's git origin remote when --repo is omitted (currently GitHub / GitLab):

rupu issues list --state open --label triage   # list issues
rupu issues show github:owner/repo/issues/42    # full body + metadata
rupu issues run <workflow> #42                  # run a workflow against an issue

Run a workflow against an issue

rupu issues run is a convenience wrapper for the canonical form, which takes the issue ref as a positional run-target:

rupu workflow run <workflow> github:owner/repo/issues/42

Issue targets do not clone — the workflow runs in the current checkout and binds the issue's metadata into step prompts and when: filters as {{ issue.* }}:

Multiple accounts per platform

A single GitHub (or GitLab) account needs none of this — [scm.github], or just a stored credential, resolves as before. To hold two accounts of one platform — a work and a personal identity, or github.com alongside a GitHub Enterprise host — name them. [scm.<name>] is account-keyed: the table name is the identity and kind selects the vendor client.

# declares the account (writes [scm.<name>] kind = ...) and stores its credential in one step
rupu auth login --account gh-work     --kind github --mode sso
rupu auth login --account gh-personal --kind github --mode sso
[scm.gh-work]
kind = "github"

[scm.gh-personal]
kind = "github"

[scm.corp-ghe]
kind = "github"
base_url = "https://git.example.internal/api/v3"   # GitHub Enterprise

# which account serves which repo
[[scm.rules]]
owner = "example-org/*"
account = "gh-work"

[[scm.rules]]
path = "~/Code/work/*"
account = "gh-work"

Each rule sets exactly one of owner (a glob on the repo owner) or path (a glob on the caller's working directory). Account selection runs in a fixed precedence, highest first:

  1. Explicit — --account <name> on rupu issues list|show, or an account argument on an scm.* / issues.* MCP tool.
  2. Owner rule — the first matching owner glob. This is the tier daemons rely on: a webhook or cron poll knows the repo owner but has no cwd.
  3. Path rule — the first matching path glob.
  4. Sole account — only one account of that platform is configured, so nothing is ambiguous.
  5. Error — never a silent guess.

A targeted call that matches no rule with two or more candidates fails with the configured accounts and a ready-made fix line; a rule that names an account with no live credential fails too, instead of falling through to a different identity. rupu repos list and scm.repos.list, which have no repo to key on, fan out across every account of the platform and tag each row with its account.

rupu scm accounts                                     # accounts, kinds, base_urls, and the rules pointing at each
rupu scm bind --owner 'example-org/*' --account gh-work  # append an owner rule
rupu scm bind --path  '~/Code/oss/*'  --account gh-personal
rupu issues list --repo github:other/thing --account gh-work   # one-off override
Run targets resolve by rule only. rupu run <target>, rupu workflow run <target> and rupu issues run have no --account flag; for an ambiguous repo, add a rule with rupu scm bind.

How it fits together

The integrations close a loop. A new or labeled issue (or a tracker state change) wakes a workflow or an autoflow; rupu's agents do the work in a cloned checkout; the SCM connector opens a PR / MR with the result; and the issue connector posts a comment back so the conversation stays where your team already lives.

Cross-references: Autoflows drive the long-running issue→PR loop with branch ownership; Triggers cover the polling and webhook tiers that wake workflows on tracker and SCM events.

Auth for integrations

Each platform stores its credential in ~/.rupu/auth.json via one command. These are SCM / tracker credentials — distinct from model-provider auth (for that, see Providers & Auth).

rupu auth login --provider <github|gitlab|linear|jira> --mode <api-key|sso>
rupu auth login --account <name> --kind <github|gitlab> --mode <api-key|sso>   # a named account
rupu auth status     # SCM + tracker rows appear automatically
  • GitHub — classic PAT (repo, workflow, gist, read:org, read:user) or a device-code SSO flow.
  • GitLab — PAT (api, read_user, read_repository, write_repository) or browser-callback PKCE SSO. See GitLab SSO below.
  • Linear — API-key mode (used for polling / webhook normalization).
  • Jira — API-key mode; store the credential as <email>:<api_token> in one secret for Jira Cloud polling.

GitLab SSO and token refresh

On gitlab.com, rupu auth login --provider gitlab --mode sso signs in as the GitLab CLI's (glab's) public OAuth application, the way GitHub SSO uses gh's. A self-managed instance needs its own OAuth application: set its Application ID as oauth_client_id on the account in the global ~/.rupu/config.toml, and the authorize and token endpoints are derived from base_url:

[scm.gl-corp]
kind = "gitlab"
base_url = "https://gitlab.example.internal/api/v4"
oauth_client_id = "<application id>"

GitLab OAuth access tokens expire two hours after issue. Every GitLab connector refreshes its token through the credential store when it is within five minutes of expiry — so a long-lived rupu cp serve, rupu mcp serve or session keeps working — and the rotated token is saved under the store's lock for every other process. A request GitLab refuses with a 401 is retried once with the latest stored token, so a fresh rupu auth login reaches processes that are already running. GitHub SSO tokens don't expire.

Webhook secrets are different. The secrets for rupu webhook serve are read from environment variables only — never config files, never the credential store: RUPU_GITHUB_WEBHOOK_SECRET, RUPU_GITLAB_WEBHOOK_TOKEN (GitLab’s shared token, not a signing secret), RUPU_LINEAR_WEBHOOK_SECRET and RUPU_JIRA_WEBHOOK_SECRET. Set only the vendors you receive from. See Triggers.
