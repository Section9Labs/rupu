Control plane

A local web app for rupu — launch runs, watch them stream live, author agents and workflows, and review findings and coverage, all in one browser tab.

A web command center

The control plane is rupu's window onto everything it's doing on this host. One command opens a browser UI where you can observe every run, session, and event as it happens; control what runs and approve the steps that ask for it; and author your agents and workflows — without leaving the page. It's a thin web adapter over the same on-disk stores the CLI uses (your runs, agents, workflows, sessions, and the coverage ledger under ~/.rupu/), so the browser and the terminal are always looking at the same reality.

Start it with one command:

# serve the control plane and open it in your browser
$ rupu cp serve

By default it binds to 127.0.0.1:7878 and opens the URL in your browser when you run it interactively. Useful flags: --bind <addr> to choose a different address or port, --token <token> to guard the API with a bearer token, and --no-open to print the URL without launching a browser. 

# bind a custom port and require a bearer token on /api/*
$ rupu cp serve --bind 127.0.0.1:9000 --token "$RUPU_CP_TOKEN" --no-open
Single binary, no setup. The web UI is compiled into the rupu binary — there's nothing to install or build. rupu cp serve serves the embedded app and reads your existing file-based stores directly; there is no database.

Observe

The observability surface is the heart of the control plane — watch everything rupu is doing, live, in the browser.

  • Dashboard. An at-a-glance landing page with aggregated counts and charts, including multi-model token spend over time so you can see what each provider is costing you.
  • Runs. A list of every run, and a live run view that paints the workflow's real graph — a split: forks and a join: merges, rather than everything flattening into one line — with each step's status updating in place, plus a streaming transcript of the focused step, unit or sub-agent as it works. Runs, steps, units and sub-agents carry their codenames, tinted per crew.
  • Live Events. A full-screen wall for everything happening across the host: a vitals strip (active runs, runs awaiting you, findings by severity, events per minute, errors), a searchable, newest-first stream that merges the live event firehose with newly filed findings — each card with the run, step and codename it came from — and a roster with one card per project showing what it's doing right now. A source that fails to load reads as idle, never as made-up activity.
  • Sessions. Every session, with its transcript streaming token-by-token.
  • Usage. Spend over time, pivoted by model, provider, agent, workflow, host or project, with an outlier panel for runs that cost far more than their workflow usually does and a banner that counts unpriced spend instead of hiding it. Usage comes from a per-run ledger written as tokens are spent, so in-flight steps, retried fan-out units, sub-agents and compaction calls all count, and a running run's or session's totals move while you watch.
  • Coverage & Findings. The coverage status of each project and the findings filed against it, read from the coverage ledger (see Findings below).
  • Agentiflows. A list of agentiflow runs and a detail page with Flow, Assets, Findings, Messages, Transcript and Events tabs: the goals and budget, the units the lead dispatched, the asset inventory the fleet built, the run's findings across every sub-run, and the message board the agents talk on. While the run is live, a steering box on the Messages tab sends the lead a message, the same channel as rupu agentiflow send. A Security → Assets page shows the asset inventory across every project.
  • Network. The netflow explorer at run, project and global scope.

Live updates arrive over server-sent events: a global stream for the event timeline and per-run streams for each run view. Runs the control plane started stream straight from the executor; runs started elsewhere (the CLI, a cron trigger, an autoflow) are tailed from their on-disk event log — so the same live view works no matter what kicked the run off.

Transcripts

The transcript view renders every event a run records, in the order it happened: the seed prompt, each turn's thinking in position (not hoisted to the top), replies, tool calls and their audits, gate pauses and decisions, notices, context compaction, and the outcome and recovery events written when a reply needed recovering. Turns are grouped, each with its own token count. A line the viewer doesn't recognise is shown as raw data with an unparsed badge rather than dropped, so a transcript from a newer rupu never silently loses content.

Findings

Each finding has its own page at /findings/<id>. A finding recorded as a full report opens with a section rail (description, impact, location, root cause, call chain, evidence, proof-of-concept artifacts, replication, remediation, patch, CI/CD and regression commands, references), a ledger of ownership and risk fields, and a completeness meter (n/11) that names the gaps. Every evidence claim carries a badge saying whether the file still matches what the agent saw (current, changed, missing), and the artifact browser previews text and images and pulls a remote host's artifacts on first view. Reports export to Markdown, HTML or PDF.

The findings tables triage in place: expand a row for root cause, attack path, owner and completeness; filter with a one-line query bar (severity>=high tag:needs-poc -tag:false-positive "sql injection") that suggests keys and values as you type and flags a bad token inline; and tag findings one at a time from a finding's page or in bulk from a table selection, with every change kept in a per-project tag history. See Findings for the report format, the query language and tagging.

Many hosts, loaded host by host

With remote hosts registered, the Activity tables, the Usage headline and the ⌘K palette's runs and sessions ask each host on its own and merge the answers as they arrive. A fast host paints at once; a slow one fills in when it answers; an unreachable one is marked offline (or unavailable when its rupu is too old to answer) without holding back the rest. A per-host freshness strip shows who has answered. Pages that read history are served from in-process caches that are re-checked against the files on every request, so opening a page doesn't re-read every run ever recorded.

Control

Beyond watching, the control plane drives rupu from the browser:

  • Launch runs. Dispatch a workflow or an agent with a target and a permission mode, straight from the UI.
  • Approve & reject gated steps. When a run pauses at a gate awaiting approval, approve or reject it in place — per gate, when a graph workflow has several parked at once. Approve marks the run for resume; a background resume worker inside rupu cp serve claims the marked run and finishes the gate. A resume requested from the browser never retries a run that finished in the meantime.
  • Cancel & pause. Cancel or pause a run from its run view. Runs are detached processes, so the browser signals them: cancel sends the recorded runner a SIGTERM (a run parked at a single gate with no live runner is cancelled by rejecting it), and pause leaves a marker the runner picks up at its next safe boundary. Only workflow runs pause: a standalone agent run has no safe boundary, so pausing one is refused (409). A paused run shows a Resume button; the resume worker continues it, picking up interrupted steps from their transcripts rather than restarting them. A button press means recorded; the run's status on the live stream is what confirms it.
  • Drive sessions. Send a prompt to a live session and watch the turn stream back as a chat.
  • Manage autoflows. See and manage your autoflows — the scheduled, trigger-driven workflows — from the same place you watch them run.
  • Archive, restore & delete. Tidy up the workspace by archiving finished runs and sessions (moving them out of the active lists without losing them), restoring them when you need them back, or deleting them for good. Archiving never deletes anything by itself: archived items are removed only when you prune them with rupu session prune, rupu transcript prune or rupu cleanup. The [storage] section's archived_session_retention and archived_transcript_retention (e.g. 30d) are those commands' default age cutoffs.
Same engine, new surface. The control plane doesn't reimplement any logic — launching, approving, and sending all route through the very same code the CLI uses. The browser is just another way in. Everything the UI does goes through the control plane's HTTP API, which you can script too — see the API reference.

Author

You can edit your agents (.md) and workflows (.yaml) right in the browser. Agents open in a code editor; workflows open in the visual workflow editor.

The workflow editor is a single screen: a drag-and-drop DAG on top and the live YAML below, kept in lock-step. Drag node cards from a palette onto the canvas, wire steps left→right exactly like the Runs graph, and watch the YAML rewrite itself underneath — or type in the YAML and watch the graph reconcile as you go. YAML stays the source of truth: the graph is a projection of it, and every save passes through the same validation the orchestrator already applies.

Every step kind has its own shape. The Flow Designer paints nodes as flowchart silhouettes rather than identical cards, so a workflow still reads when it's zoomed out far enough to see whole: a branch is a decision diamond, an action connector a parallelogram, an approval gate the trapezoid of a manual operation, a for_each a hexagon, and parallel / panel keep growing rectangular bodies for their sub-steps. Connection handles anchor to the silhouette itself, so nodes drag and wire by their real shape — and shape carries the kind independently of colour.

A Blocks palette with its own tab. The rail is one tab bar — Blocks · Step · Settings · Reference — so the palette and the editor no longer compete for height. Blocks sits on a dense chip grid with a filter across both the step kinds and the whole connector catalog, each chip previewing the silhouette it will place. Selecting a chip shows what it does, its required fields, and a short example before you commit it; drag-to-place or Add to canvas drops the node and jumps you straight to its form.

Per-kind authoring forms. The Step tab renders the form the selected node actually needs. Connector (action) steps get a form generated from the tool catalog's own JSON schema — required parameters marked, values that round-trip whether they're numbers, booleans, lists, or {{ … }} expressions — so new tools appear in the editor with no editor changes. Approval gates get editors for their notify hooks and their on-reject cleanup steps; panels and branches get their sub-schemas, with constrained choices (severity thresholds, minimums) instead of free text you can typo into a failed run.

One visual language, author and run. The live run graph now paints from the same kind palette as the editor, with connectors animating along the active path — kind colour carries identity while status stays the overlay, so a running step pulses, a gate awaiting you glows amber, and a failure still reads as a failure. Watching a run and editing it look like the same thing.

Every expression field — a step's prompt, when, a branch's condition, or a panel's subject — gets syntax highlighting and context-aware autocomplete. Inside {{ … }} it suggests the right vocabulary for where you are: declared inputs, the outputs of steps that run before this one (never a forward reference), loop locals like item inside a for_each, panel findings, and the available filters. A searchable expression reference panel surfaces the whole vocabulary and inserts at the cursor. Validity is checked live — at the field, on the node, and in a header badge — so mistakes show up before you ever save.

Settings & project config

You can edit rupu's configuration from the browser. A global Settings page writes the global ~/.rupu/config.toml, and a Config tab on each Project detail view writes that project's .rupu/config.toml. Config is layered global global → customer → project → env, and the control planerarr; customer global → customer → project → env, and the control planerarr; project (a locked key in a higher layer wins; see Configuration), and the control plane shows the effective value for every key together with its provenance — which layer won.

Each surface is hybrid: a typed Form tab with per-field validation, plus a raw TOML tab with validate-on-save, both writing the same file. Alongside them sit a policy view (what's locked) and a runtime status view — the latter shows restart-required settings such as bind and token read-only (the token masked).

Policy enforcement. An admin can lock specific settings at the global level so projects — and the UI — can't override them. Locked keys are pinned to the global value wherever config is resolved (CLI, agent runs, cron, and the control plane alike), and appear read-only on the project Config tab. Locks are declared as dotted key paths in a [policy] section of the global config: 

# ~/.rupu/config.toml — lock keys so projects can't override them
[policy]
lock = ["permission_mode", "autoflow.max_active", "cp.max_workspace_bytes"]

# control-plane runtime settings live in their own section
[cp]
max_workspace_bytes = 104857600

Writes go through validated config endpoints — GET the effective config with provenance, and PUT the global config, a project's config, or the policy lock list. Every write is validated, backed up, and written atomically; project-config paths are confined under the project's .rupu/ (no path traversal), and writes require the full rupu cp serve runtime.

Models. Settings has a Models tab listing every model each configured provider offers, with its input limit, output cap and where each number came from (your [[providers.X.models]] entry or the provider's own model list, cached for an hour). Refetch pulls a fresh list from one provider or all of them. Runs resolve their limits from the same catalog — an agent's own pins win — so the context gauge and compaction use the numbers you see here.

Customers

If you work for several clients, a customer scope picker in the header narrows the whole UI to one of them — all, no customer, or a named customer. Runs, sessions, workflows, agents, findings, projects and usage follow it, and the choice is remembered in the browser. A page that can't be filtered says so rather than quietly showing everything. The Customers page manages customers and their project assignments, shows per-customer rollups priced with that customer's own pricing, and edits each customer's config layer. Before a launch, the launcher shows which customer the run will be attributed to and which provider, fallback and SCM accounts it will authenticate as — resolved exactly the way the launch itself resolves them. See Customers.

Multi-host

One control plane can drive rupu running on other machines, not just the one it's on. Register a remote host — over HTTP, SSH, a dial-home tunnel, or an object-store bucket — and launch runs, agents, and sessions on a chosen host, observe and control them, all from one browser, with a Fleet → Hosts surface and host filtering on run lists. See Multi-host for setup and the transport roadmap.

UI tour

A page-by-page map of the web app, with the route each page lives at. Every route can be bookmarked or shared, and the ⌘K command palette jumps to any of them.

Two navigation shells

The app ships two sidebars over the same pages. The default (v1) shell lists every page in grouped sections — Runs, Security, Build, Fleet. The newer v2 shell folds them into seven destinations (/overview, /activity, /projects, /security, /library, /fleet, plus Customers), each a tab bar whose active tab sits in ?tab=. Old links keep working: under v2, /agents redirects to /library?tab=agents, /hosts to /fleet, and so on. Pick the shell in the global config; a browser refresh applies it, no restart needed: 

# ~/.rupu/config.toml — opt into the v2 navigation shell
[ui.cp]
shell = "v2"
v2 destinationTabs
/overviewThe dashboard.
/activityagents · workflows · autoflows · sessions (run lists)
/securityfindings · coverage · catalog
/libraryagents · workflows · autoflows (definitions)
/fleethosts · workers

Settings

/settings has typed tabs for General, Providers, Models, Autoflow, SCM / Issues, Pricing and CP-Runtime, then Raw (the global config.toml, read-only until you click Edit), Policy (every key with a lock checkbox), and Runtime status. Each typed field shows its effective value, which layer it came from, and a lock toggle. The control plane's own bearer token is never shown or editable, only whether one is set.

Customers

/customers and /customers/<slug> (with a tab per sub-route) manage customers; see Customers above.
