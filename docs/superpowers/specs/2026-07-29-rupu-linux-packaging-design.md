# rupu Linux packaging — design

**Date:** 2026-07-29
**Status:** approved, pending implementation plan
**Scope:** native `.deb` / `.rpm` packages, hosted APT + YUM repositories, and
community-format packaging (AUR, Homebrew, Nix).

**Depends on:** the cross-platform release arc
(`docs/superpowers/specs/2026-07-27-rupu-cross-platform-release-design.md`). As of
`v0.70.3-beta` the release workflow publishes static musl binaries for `linux-x64` and
`linux-arm64`; this design consumes those artifacts rather than building anything new.

## Problem

Linux users can download a binary, and that is all. Three gaps follow:

1. **Runtime dependencies are undeclared.** rupu shells out to `rg` and hard-errors without
   it. This was not discovered by reading the code — it surfaced when the first Linux CI run
   failed with `` Execution("`rg` (ripgrep) not found in PATH") ``. A tarball cannot express
   that requirement; a package can, and the package manager resolves it before the user ever
   sees a broken tool.
2. **No system integration.** `rupu completions <shell>` exists but nothing installs its
   output to the paths shells actually read. There is no man page.
3. **No system-native install or upgrade.** Every update is a manual download. On a machine
   where rupu is deployed rather than developed, that is the wrong shape entirely.

## Decisions taken

| Decision | Choice | Consequence |
|---|---|---|
| Scope | `.deb`/`.rpm` assets **and** hosted repos **and** community formats | Three phases; each ships usable value alone |
| Build tool | `nfpm` | One config emits both formats from an already-built binary |
| Signing | A new dedicated GPG key, private half held by the maintainer, copy in CI | Blast radius limited to package signing; revocable without touching anything else |
| Repo hosting | GitHub Pages | Free, same org users already trust, no new accounts |
| Repo index contents | **Latest version only** | ~100 MiB forever; every version remains installable from release assets |
| Self-update on packaged installs | Refuse, with a message | Two update mechanisms never fight |

### Why the index carries only the latest version

GitHub Releases and GitHub Pages are not comparable stores. Releases allow 2 GiB per asset,
have no documented cap on total release storage, and release assets do not count against the
repository size limit. Pages soft-caps the published site near 1 GB.

So the split follows the strengths: **every version's packages stay release assets forever**,
while the Pages-hosted index carries only the current one. At roughly 100 MiB per version
(2 architectures × 2 formats) the site stays near 100 MiB permanently, and the repo-generation
job needs no pruning logic — it regenerates from the current release each time.

**The trade-off, stated plainly:** `apt install rupu=0.70.1` will not work for any version
that is not current, because apt can only install what the index advertises. `apt install`
and `apt upgrade` are unaffected — both want the newest version anyway. Downgrading or
pinning means fetching that `.deb` from its GitHub release and running `dpkg -i`, which is
already how people handle tools distributed this way.

If version pinning through apt is wanted later, moving from "latest only" to "last N indices"
is purely additive. Going the other way — from "keep everything" to pruning, after hitting
the Pages ceiling — is the painful direction, which is why this design does not start there.

## Design

### 1. Package contents and metadata

Each package installs:

| Path | Contents |
|---|---|
| `/usr/bin/rupu` | the static musl binary from the existing release job |
| `/usr/share/bash-completion/completions/rupu` | generated by `rupu completions bash` |
| `/usr/share/zsh/site-functions/_rupu` | generated by `rupu completions zsh` |
| `/usr/share/fish/vendor_completions.d/rupu.fish` | generated by `rupu completions fish` |
| `/usr/share/man/man1/rupu.1.gz` | generated man page (none exists today) |
| `/usr/share/doc/rupu/` | README, LICENSE |

Completions are generated at package-build time by running the binary being packaged, so they
cannot drift from the CLI surface they describe.

**Dependencies**, classified by reading the actual failure behavior rather than assuming:

| Package | Relationship | Why |
|---|---|---|
| `ripgrep` | **Depends** | `crates/rupu-tools/src/grep.rs` resolves `rg` via `which` and returns a hard `Execution` error without it. The grep tool is unusable. |
| `git` | **Recommends** | `crates/rupu-cli/src/cmd/init.rs` prints "git not found on PATH; skipping" and continues. libgit2 is vendored statically, so core repository operations do not need the `git` binary at all. |
| `ast-grep` | **Suggests** | `crates/rupu-tools/src/ast_grep.rs` returns empty output with an explanatory message when absent. |

**On static linking.** Shipping a statically-linked binary in a `.deb` is contrary to Debian
*archive* policy, and would block inclusion in Debian main. It is normal and accepted for
third-party repositories, and is how most Go and Rust tools distribute. This design does not
target Debian main or Fedora's official repositories; see Out of scope.

### 2. How packages are built

`nfpm`: one YAML config emits both `.deb` and `.rpm` from an already-built binary. It joins
the existing release workflow as a job that consumes the `asset-linux-x64` and
`asset-linux-arm64` artifacts. **Nothing about the binary build changes** — the musl container
and its guarantees stay exactly as they are.

Four packages per release:

| Format | nfpm arch | Resulting arch string |
|---|---|---|
| `.deb` | `amd64` | `amd64` |
| `.deb` | `arm64` | `arm64` |
| `.rpm` | `amd64` | `x86_64` |
| `.rpm` | `arm64` | `aarch64` |

The architecture naming differs between formats; nfpm handles the translation, and the
implementation must verify the emitted filenames rather than assume.

`cargo-deb` and `cargo-generate-rpm` are rejected deliberately: both want to drive the cargo
build themselves, which would mean building Linux binaries a second time outside the pinned
musl container and losing the guarantee that the packaged binary is the one that was tested.

### 3. Signing and repository hosting

A dedicated GPG key signs both the packages and the repository indices. It is generated once,
the private half is handed to the maintainer to store, and a copy lives in CI as a repository
secret alongside the existing Apple credentials. The public key is published at a stable URL
that users fetch during setup.

The repositories are generated by a job that takes the current release's four packages and
builds:

- **APT** — `Packages`, `Packages.gz`, and a detached-signed `Release` / `InRelease`
- **YUM** — `repodata/` with a signed `repomd.xml`

Both are published to GitHub Pages. Setup for users is a two-line snippet per distro family,
documented in the README.

### 4. `rupu update` on packaged installs

The package build stamps `RUPU_INSTALL_METHOD=deb` (or `rpm`) into the binary via
`option_env!` in `crates/rupu-cli/src/build_info.rs` — the same mechanism already used for
`RUPU_RELEASE_CHANNEL` and `RUPU_RELEASE_VERSION`, so this introduces no new pattern.

Behavior when that marker is present:

- `rupu update` **refuses**, with `installed via apt — run 'sudo apt upgrade rupu' instead`
  (or `dnf upgrade` for rpm).
- `rupu update --check` **still works** and still reports that a newer version exists. The
  user should be able to learn they are behind regardless of how they installed.
- `rupu update --rollback` refuses for the same reason.

Tarball and `install.sh` installs carry no marker and are entirely unaffected.

Without this, the two mechanisms actively fight: writing to root-owned `/usr/bin/rupu`
requires sudo, and any self-update that did succeed would be silently reverted by the next
`apt upgrade` — leaving a user watching their version go backwards for no visible reason.

### 5. Community formats

Three, all of which consume the release assets and checksums already published, and none of
which require changes to the release workflow:

- **AUR** — a `PKGBUILD` for Arch, referencing the `linux-x64`/`linux-arm64` assets and their
  `.sha256` sidecars.
- **Homebrew tap** — `Section9Labs/homebrew-tap`. Works on Linux as well as macOS, and gives
  macOS users a `brew install` path they do not have today.
- **Nix flake** — a derivation pinned to the release assets by hash.

### 6. Phasing

**Phase A — packages as release assets.** The nfpm job, the four signed packages, the man
page, completions generation, and the `RUPU_INSTALL_METHOD` marker with its `rupu update`
behavior. Delivers `dpkg -i` / `dnf install ./rupu.rpm` on its own.

**Phase B — hosted repositories.** GPG key generation and CI wiring, index generation, Pages
publishing, and the README setup snippets. Upgrades Phase A into `apt install rupu` and
`apt upgrade`.

**Phase C — community formats.** AUR, Homebrew tap, Nix flake. Independent of A and B beyond
needing release assets to exist, so it can land at any point.

## Risks

- **Architecture naming.** `.deb` uses `amd64`/`arm64`, `.rpm` uses `x86_64`/`aarch64`. A
  mismatch produces a package that installs on the wrong machine or refuses to install on the
  right one. The implementation must assert the emitted filenames.
- **GPG key rotation.** The key will eventually expire or need rotating, and every user who
  added it must then re-import. Set a long expiry and document the rotation procedure at the
  same time the key is created, not later.
- **Pages build limits.** GitHub Pages allows roughly 10 builds per hour. Not a constraint at
  a normal release cadence, but a burst of re-releases could hit it.
- **`sources.list` format.** Debian is migrating from the one-line format to deb822
  (`.sources`). The documented snippet should use the modern format with the legacy one noted,
  since Ubuntu LTS releases still in support understand only the latter.
- **Package-manager metadata is a compatibility surface.** Renaming the package, or changing
  its architecture strings, breaks upgrades for everyone already installed. Get the names
  right in Phase A.

## Out of scope

- **Debian main / Fedora official repositories.** Both would require unbundling vendored
  dependencies and dynamic linking — a fundamentally different build, not an extension of
  this one.
- **Snap and Flatpak.** Their sandboxing is actively hostile to what rupu is: a tool that
  spawns arbitrary processes, reads and writes arbitrary paths in the user's projects, and
  shells out to `git` and `rg`. A confined rupu would be a broken rupu.
- **Alpine `apk`.** The static musl binary already runs on Alpine; a native package can follow
  if demand appears.
- **Windows packaging** (winget, Chocolatey, MSI). WSL2 remains the Windows story per the
  cross-platform spec.
- **32-bit architectures**, and Linux architectures beyond x86_64 and aarch64.
