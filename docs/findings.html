Findings

A finding is recorded once, as structured data. That record is the source of truth: rupu renders the report page, the Markdown, HTML and PDF exports, and every list and query from it, so an agent never writes a separate report file.

Findings are written by the coverage harness’s report_finding tool (and the findings.record MCP action). This page covers what a finding report contains, how to query and tag findings, and how to export, import and download them.

Finding profiles

Every finding is written under one of two profiles:

ProfileWhat report_finding / findings.record accepts
full (default)A complete report object. summary, severity and evidence are rejected: rupu derives them (summary ← title, severity ← rating.risk_rating, evidence.rationale ← root_cause).
summaryThe lightweight summary / severity / evidence record. A report is refused, never silently dropped.

The profile is chosen, highest precedence first, by:

  1. a workflow step’s findings_profile, or rupu run --findings-profile for a standalone run;
  2. the workflow’s defaults.findings_profile;
  3. the agent’s findingsProfile frontmatter;
  4. the built-in default, full.

Remote workflow units (host: / distribute:) resolve the same way; the value travels to the host as --findings-profile, and a connector refuses a profile its peer doesn’t advertise rather than dropping it. The profile is stored on each finding; records written before profiles existed read back as summary.

---
name: quick-triage
findingsProfile: summary      # this agent records thin findings
concerns:
  - include: owasp-top10-2021
---
Upgrading. Because the default is full, an older agent that records thin findings is rejected until it declares findingsProfile: summary or its prompt is updated to send a report. When a full-profile run can record findings, finding-writing guidance is appended to its system prompt automatically, so no external reporting-standard file is needed.

What a full report contains

A full report has these fields; every one is required except cwe (which may be an empty list), artifacts, blocks and classifications:

GroupFields
Identitytitle, category, attack_vector, cwe (CWE-<n> ids)
Ownershipownership (owner, product, affected_component, source_repository), tickets
Ratingrating: impact, risk_rating, risk_factor (Low/Medium/High/Critical), likelihood (Low/Medium/High), cvss_v3
Narrativedescription, impact, location (input / output), root_cause, call_chain (source → hop → sink)
Proofevidence (at least one claim, each optionally pinned to a workspace-relative file + lines), replication_steps (at least one), artifacts, blocks
Fixremediation, recommended_patch (a unified diff), ci_cd_detection, regression_test
Linkscross_references (existing finding ids), references

Rules are enforced at write time, and a rejected call returns every problem at once with its field path, so the agent can fix them all in one retry. The serialized report must fit [findings].report_max_bytes (default 256 KiB). Some fields are set by rupu, never by the agent: the verification status (set by verification runs), each evidence claim’s sha256 (rupu hashes the claim’s file), and an artifact’s hash, size, kind and storage.

Sentinels

Where information genuinely cannot be determined, a field uses a sentinel instead of being omitted or guessed. On the structured fields only the exact sentinels listed for that field are accepted.

SentinelUsed for
Unknownowner, product, affected component, source repository, attack vector, CVSS score, tickets
Not Applicablesource repository, when no source-controlled code is involved
None Providedtickets, when none are mentioned
Nonecross references, when there is no related finding
Not Provided — <justification>call chain, recommended patch, CI/CD detection, regression test (the justification must be non-empty)

Unknown is not accepted for the patch, CI/CD detection or regression test: provide the item or say why it could not be produced.

Evidence blocks

Alongside the prose evidence claims, a report may carry typed blocks, each an object tagged by kind:

text   code_slice   diff   table   image   hexdump
disasm   decompile   http_exchange   scan_output   pcap_ref

Three of them name a file: image (plus an optional caption), hexdump (a base address and an optional rendered dump) and pcap_ref (a summary). That file, in the block’s artifact.path, is verified and stored exactly like a proof-of-concept artifact (below) and counts against the same per-finding limits, but it doesn’t appear in the PoC list. The control plane renders every block kind in an “Evidence blocks” section, with image blocks shown inline.

{ "kind": "http_exchange",
  "request":  "GET /api/notes?sort=title%27-- HTTP/1.1\nHost: notes.example.test",
  "response": "HTTP/1.1 500 Internal Server Error\n..." }

{ "kind": "image",
  "artifact": { "path": "poc/error-page.png" },
  "caption": "Stack trace leaked by the sort parameter" }

Artifacts and the content-addressed store

report.artifacts[].path lists proof-of-concept files (scripts, outputs, harnesses) as workspace-relative paths; the agent supplies only the path. At write time rupu hashes each one:

  • A file up to [findings].artifact_max_bytes (default 500 MiB) is copied into a content-addressed store at <RUPU_HOME>/findings/artifacts/<aa>/<sha256> and recorded stored: copied. Identical content is stored once across runs and projects, and the store outlives the workspace.
  • A larger file is recorded stored: external with its path, size and sha256.
  • A directory expands to the files inside it (symlinks inside are skipped).
  • One report is bounded to artifact_max_files files (default 500) and artifact_total_max_bytes copied (default 2 GiB).
  • A path that escapes the workspace, doesn’t exist, or isn’t a regular file rejects the finding, so a typo is never silently dropped.
[findings]
artifact_max_bytes       = 524288000    # copy cap per artifact file (500 MiB)
artifact_max_files       = 500          # files per report
artifact_total_max_bytes = 2147483648   # bytes copied per report (2 GiB)
report_max_bytes         = 262144       # serialized report budget (256 KiB)
ticket_patterns          = ["ABC-[0-9]+"] # extra ticket formats for the guidance
export_id_prefix         = "VULN"       # export numbering prefix (global config only)

Remote artifacts, pulled on view

A remote workflow unit records its findings on the host, so its artifacts land in that host’s store. The unit’s coverage stream (findings included) reaches the coordinator when the unit ends, and the coordinator records those artifacts as stored: external with the host’s id. The bytes stay on the host until someone views them: the first preview or download through the control plane pulls the blob over whatever transport the host uses (SSH, HTTP, tunnel or bucket), checks it against the recorded size and sha256, and keeps it in the coordinator’s store. Concurrent first views share one pull. If the bytes can’t be had (host offline, blob missing, over the coordinator’s size cap, failed verification), the response is a 404 naming the reason, nothing is stored, and the next view tries again.

Artifacts are served with nosniff and a sandboxing Content-Security-Policy: text inline as plain text, PNG/JPEG/GIF/WebP images inline (recognised by their bytes, never by name), everything else as a download. Opening a finding never pulls from a host on its own; a remote image block loads only when you click it.

rupu findings schema

rupu findings schema                 Print the embedded draft-07 JSON Schema of a finding report
rupu findings schema --advertised    Print the simplified copy used in tool definitions

The schema is embedded in the binary and held in lockstep with the validator by a test, so external prompts and tools can be generated from rupu rather than maintained by hand.

Querying findings

One single-line query language filters findings on every surface: rupu findings list and tags, the agent tool query_findings, the MCP tool findings.query, and the control plane’s Findings page. One evaluator serves all of them, so a query means the same thing everywhere.

severity>=high tag:class:sqli -tag:false-positive -has:poc "sql injection"

Grammar

  • Tokens are separated by whitespace and every token must match (AND). Repeating a key ANDs too: tag:a tag:b needs both tags.
  • key:value filters a field; key:a,b matches any of the values (OR within one token); -key:value negates it.
  • Only severity takes >=, >, <=, <, with a single value.
  • A bare word or quoted phrase is free text, matched case-insensitively against title, summary, id and file path; -word negates it.
  • A token shaped like a key plus an operator always names a key, so an unknown key is an error, never text. Quote text that contains a colon: "http://host".
  • Only the first : after the key splits, so tag:class:sqli works.

An invalid query never runs. It is refused with the offending token’s index and a code: unknown_key, empty_value, bad_value, bad_operator, unclosed_quote or bad_quote.

Fields

KeyMatches
severity (sev)info, low, medium, high, critical; also >=, >, <=, <
tagan effective tag (normalized, so Class:SQLi is class:sqli)
hastags, report, poc (the report has artifacts), cwe
projectworkspace name or id (CLI and control plane only)
cwe79 or CWE-79, compared by number — CWE-79 never matches CWE-798
owner, productthe report’s ownership, case-insensitive
verifiedunverified, confirmed, disputed, inconclusive
profilefull, summary
scopeline, file, repo, host, endpoint, resource
concernconcern id, case-insensitive
agentagent name or codename, case-insensitive
workflowworkflow name (CLI and control plane only)
filepath prefix
runrun id; the CLI and control plane also match the run’s sub-runs
idfinding id

Examples

# quote anything your shell would treat as a redirect: > and < are redirects
rupu findings list 'severity>=high' tag:needs-poc -has:poc
rupu findings list 'owner:"payments team"' profile:full
rupu findings list --limit 20 cwe:89,79 file:src/api/
rupu findings list --ids-only -has:tags
rupu --format json findings list verified:confirmed project:notes-service

list spans every registered project; put --limit N and --ids-only before the query words. An agent with query_findings in its tools: (or a workflow action: findings.query step) sends {q, limit, cursor}; limit defaults to 50 (at most 500), or all: true returns every match unpaged — handy for fanning out over the results:

steps:
  - id: tagged
    action: findings.query
    with: { q: "tag:needs-poc severity>=high", all: true }
  - id: poc
    agent: poc-writer
    for_each: "{{ (steps.tagged.output | fromjson).rows | tojson }}"
    max_parallel: 4
    prompt: |
      Write a proof of concept for finding {{ item.id }}: {{ item.title }}.

The agent tool and MCP work only on the agent’s own workspace, so they refuse project: and workflow:.

Tagging findings

A finding can carry free-form tags (needs-poc, class:sqli, status:triaged) used to sort, filter and queue work. Tags never change a finding’s report, severity or id.

  • Syntax. Trimmed and lowercased, then checked: a-z, 0-9 and . _ : / -, starting with a letter or digit, at most 64 characters (Needs-POC is stored as needs-poc). An invalid tag is rejected, never rewritten. namespace:value is a convention, not something rupu interprets.
  • Cap. At most 32 tags per finding.
  • Where they live. Tags a finding was declared with sit on its record in findings.jsonl. Every later add or remove is an event in one append-only file per workspace, .rupu/coverage/finding_tags.jsonl, folded on read in file order. Each event records who made it: an agent’s run/agent/model, or an operator via the CLI or the control plane.

Who can tag

WhoHow
Agentsreport_finding takes an optional tags array. query_findings and tag_findings are explicit tools: grants; tag_findings is allowed in readonly mode since it never touches workspace files. query_findings also returns tags_in_use, so agents reuse tags instead of inventing near-duplicates.
Workflow stepsMCP actions findings.query and findings.tag; findings.record accepts tags. These are for action: steps only; an agent is never offered them, even with tools: ["*"].
Operatorsrupu findings tag / tags, or the control plane.
 
rupu findings tag fnd_01J… --add needs-poc --add class:sqli
rupu findings tag fnd_01J… --remove needs-poc
rupu findings tags                       # tags in use, with counts
rupu findings tags severity:critical      # ...over the findings a query selects

# tag everything a query matches: a lone `-` reads ids from stdin
rupu findings list --ids-only tag:class:sqli | rupu findings tag - --add needs-poc
# a workflow action step
- id: mark
  action: findings.tag
  with: { finding_ids: ["fnd_01J…"], add: ["needs-poc"] }

rupu findings tag works across projects, atomically per workspace: an unknown id or a workspace that couldn’t be changed makes it exit non-zero after the others have kept their changes. Tags added by a remote unit travel back in its coverage stream and are merged into the coordinator’s tag log by event id.

Exporting reports

A stored finding exports as Markdown, self-contained HTML, or PDF — one finding, or a whole project. All three carry the same sections in the same order, and every field of the report.

rupu findings export [--id <fnd_…>]… [--project <ws_id|path>] [--run <run_id>]
                     [--severity <critical|high|medium|low|info>]
                     [--owner <name>] [--cwe <CWE-n>] [--include-summaries]
                     [--to md|html|pdf] [--split] [--title <text>] -o <path>

The document format is --to (default md), not the global --format. Filters combine; --severity keeps that severity and worse; --run includes sub-runs. A single --id alone writes a stand-alone document; anything else writes a project report over the selection (title, summary, index, then one section per finding), or with --split a zip of index.md plus one file per finding. Summary-profile findings are left out unless you pass --include-summaries. -o may be an existing directory to receive the generated file name. Finding ids are unique within a project, not across projects: when a single --id exists in several, the export refuses and names them, and --project picks one.

# one finding as a PDF, into ./reports
rupu findings export --id fnd_01J… --to pdf -o ./reports

# everything high or worse in one project, as a single HTML report
rupu findings export --project ~/src/notes-service --severity high --to html \
  --title "Notes service assessment" -o assessment.html

# one file per finding plus an index, for one run
rupu findings export --run run_01J… --to pdf --split -o run-findings.zip

Numbering

Exports number findings within their project — by severity (critical first), then declaration time, then id — as <PREFIX>-NNN (SEC-001, SEC-002, …). Numbers are assigned before any filter applies, so a finding keeps its number whatever a report leaves out, and the CLI and the control plane agree. A number is a point-in-time display label: the fnd_ id is the stable handle, and a project report’s index lists both. Files are named <NUMBER> - <Short Title>.<ext>, e.g. SEC-003 - SQL injection in the search endpoint.pdf.

The prefix is [findings].export_id_prefix (default SEC), read from the global config only — a repo’s .rupu/config.toml never changes it, since it ends up in file names and document text. It must match ^[A-Za-z][A-Za-z0-9_-]{0,15}$; anything else is ignored with a warning.

Formats

FormatNotes
mdPlain Markdown. Report text is kept as Markdown but neutralised so it can’t restructure the document (line-leading < escaped, headings demoted, unclosed fences closed). image blocks are referenced by path.
htmlOne self-contained file with inline CSS; loads nothing from the network and runs no script, with a strict embedded CSP. Raw HTML in report text is neutralised. image blocks are inlined as data: URIs.
pdfRendered in-process with Typst — no headless browser, no external tools, bundled fonts (so no CJK or emoji glyphs). Behind the default-on pdf cargo feature.

Only image blocks whose file is in this machine’s store, is a raster image by its leading bytes, is at most 4 MiB and still matches its hash are embedded; anything else is shown by path, sha256 and size with a note. An export never fetches from another host.

Importing older reports

Findings recorded before the full profile existed are summary findings whose report was written separately as Markdown. rupu findings import attaches those reports to their findings — a one-time, best-effort migration aid, not an input path.

rupu findings import <PATH>… [--id <fnd_…>] [--dry-run]
  • Input. Report files, or directories searched recursively for *.md. It reads the layout rupu findings export --to md writes, and a plain-text layout of bare section headings and Label: value fields. Files that aren’t reports (a README, an index) are skipped.
  • Which finding. The id on the report’s Finding ID: line (an id mentioned only in prose is never used); --id names it for a single file that has none.
  • Result. The finding becomes full-profile. The report goes through the same validation as report_finding and attaches whole or not at all; a finding that already has a report is skipped. Nothing is invented: a missing field with a sentinel gets the sentinel, a missing required section fails the file.
  • Safety. Each changed ledger is backed up byte-for-byte to findings.jsonl.pre-import-<UTC time> first, then replaced atomically under the ledger lock. --dry-run validates everything and prints would attach without writing anything.
Note. Run an import when no agents are recording findings, and stop long-running processes started from an older rupu first (a session worker, cp serve). Once you’ve checked the result, delete the backups — each is a full copy of the ledger.

In the control plane

The control-plane web UI (rupu cp serve) renders stored reports directly; no export step is needed to read one.

  • Report page (/findings/:id). A section rail (description, impact, location, root cause, call chain, evidence, PoC artifacts, replication steps, remediation, patch, CI/CD and regression commands, references, provenance), CWE and verification chips over a ledger of ownership and ratings, and a completeness meter n/11 that lists the gaps (an Unknown or Not Provided counts as a gap). Each evidence claim carries a badge comparing the file hash at write time with the file now: current, changed, missing or unknown. Call-chain steps link into the project’s Code tab, the patch renders as a diff, commands have copy buttons, and Markdown / HTML / PDF buttons export the finding. A summary-profile finding opens a compact page.
  • Lists and triage. The global Findings page, a project’s findings tab, coverage detail and a run’s Findings tab show a Report column (n/11 plus a PoC marker, or “summary”). Expanding a full-profile row shows a triage card — root cause, attack path, owner and product with unknowns flagged, completeness, verification status — with an “Open full report” link. An Export report button exports exactly the rows listed.
  • Query bar. The Findings page takes the same query language: press / to focus it, get fuzzy suggestions for keys and values (with counts), and see an invalid query’s error inline instead of stale results. The query lives in the URL, so /findings?q=severity%3Ahigh%20tag%3Aneeds-poc is a shareable link, and the severity tiles toggle severity:<x> in it.
  • Findings in the code. A project’s Code tab shows each finding inline, under the lines it’s pinned to, like a review comment: severity, summary and rationale, with full-profile findings adding tabs for root cause, call chain, evidence, patch and repro. Several findings on one line stack. When the project’s git remote is on github.com, gitlab.com, or a self-hosted host named by a base_url in the global config’s [scm.<account>] tables (GitHub Enterprise, self-managed GitLab), a finding with a file path also gets a View on repository link to the file on the branch the project had checked out when rupu first registered it (main if unknown), anchored to the finding’s line range (#L40-L52 on GitHub, #L40-52 on GitLab). The link isn’t pinned to a commit: rupu doesn’t record the commit a run worked on, so the lines can drift as that branch moves. The same permalink field is on finding rows from GET /api/findings; it’s absent for unrecognized hosts and findings with no file.
  • Structural search results. In a run’s transcript, an ast_grep call renders each match with its metavariable captures highlighted and listed. Click a match’s file:line:col to open a line-numbered, syntax-highlighted source preview around it, or tree to open its syntax tree: a collapsible concrete-syntax-tree viewer with the matched node highlighted and its ancestors expanded (named nodes only, with a toggle for anonymous ones). Both read the file from the run’s workspace as it is now, so they work for local runs; for a run on a remote host they say the preview isn’t available.
  • Tag editing. On a finding’s page, tags show as removable chips with a + tag input that suggests tags already in use, plus a collapsible tag history (who, when). On the Findings table, select rows and use Tag… / Untag… for bulk changes. Every change is recorded as an operator event, via: cp, in the same tag log the CLI writes, and lands only on the finding you selected, even when another project holds a finding with the same id. A project whose tag log can’t be read shows its tags read-only.

The same data is available over the API: GET /api/findings?q=… (slim rows plus facets; an invalid q is a 400 naming the token), GET /api/findings/:id (the full report with per-claim evidence status and tag history), GET /api/findings/:id/artifacts/:sha256, GET /api/findings/:id/export?format=md|html|pdf, POST /api/findings/export, and GET/POST /api/findings/tags. Because an id is unique only within its project, the per-finding routes take ?ws_id=, and answer 409 naming the projects when an id is ambiguous without it; see the HTTP API.
