Providers & Auth

rupu ships five LLM provider kinds (anthropic, openai, gemini, copilot and the generic openai-compatible) and shares its credential store with the SCM vendors (github, gitlab). Every vendor takes an API key; the vendor-specific LLM kinds and both SCM vendors also take an SSO login, and most of those have a device login for a machine with no browser. Because every agent picks its own provider, model, and credential, a single workflow can run a planner on one model and reviewers on another in the same run.

This page is the canonical reference for what works, how to configure it, and how to debug it. For the SCM side (scopes, [scm.<account>], routing) see Integrations.

The multi-provider model

rupu is not pinned to one vendor. It ships working integrations for Anthropic, OpenAI, Gemini, and GitHub Copilot, and the choice is made per agent, not globally. Each agent file declares its provider, model, and (optionally) auth mode in its YAML frontmatter — so when a workflow fans out across several agents, those agents can each talk to a different provider concurrently.

That means a real workflow might dispatch a planner step on a Claude model, two reviewer steps on GPT-5 and Gemini, and a long-context search step on Gemini's 1M-token window — all inside one run, each authenticating with its own credential.

ProviderWhat it's forAuth options

openai GPT models via the Responses API. Platform API key or ChatGPT SSO (browser callback, or Codex device auth). Different endpoints under the hood.

Those four are the built-in providers, with first-class auth flows and curated model lists. But you are not limited to them: beyond the built-ins, you can register any OpenAI-compatible HTTP endpoint as a named provider and mix it into the same workflows — see Bring your own provider below.

Accounts vs. vendor kind

A provider name used to mean two things at once: which credential to use and which vendor client to build. They are now split:

  • Account — the identity. A freeform name (anthropic, anthropic-work, openai-lab) that holds its own credential, including its own SSO token. It is what an agent's provider: field names.
  • kind — the vendor client that authenticates the account: anthropic, openai, gemini, copilot, openai-compatible (or, for SCM and trackers, github, gitlab, linear, jira).

A bare vendor name needs no kind — the account name is the vendor, so single-account setups work unchanged. To hold a second account of the same vendor (a work and a personal identity, say), give it a distinct name and its vendor with --kind the first time you log in:

rupu auth login --account anthropic-work     --kind anthropic --mode sso
rupu auth login --account anthropic-personal --kind anthropic --mode sso

The first login with --kind writes [providers.<account>] kind = "<kind>" into ~/.rupu/config.toml, so later resolution (agent frontmatter, rupu auth status, token refresh, rupu models, pricing) knows the account's vendor; after that the kind is inferred. Point an agent at an account with provider: anthropic-work. A github / gitlab account lands in [scm.<account>] instead — see Integrations. --provider remains an alias for --account.

For CI, RUPU_<ACCOUNT>_API_KEY is read as a fallback when no credential is stored (never when SSO was explicitly requested). Non-alphanumeric characters map to _, so anthropic-work reads RUPU_ANTHROPIC_WORK_API_KEY — pick account names that stay distinct once mangled.

Choosing a provider/model per agent

Provider and model are agent-level decisions. An agent file is Markdown with a YAML frontmatter block; the relevant fields are provider, model, and the optional auth:

---
name: refactor
description: Suggest minimal-diff refactors.
provider: anthropic
auth: sso
model: claude-sonnet-4-6
---

You suggest minimal-diff refactors. Be concise.

If you omit model, rupu falls back to the provider's default_model from ~/.rupu/config.toml. If you omit auth, the credential resolver applies a default precedence (SSO if present and refreshable, then API key).

Model resolution runs most-specific-wins: the agent's (or step's) model: first, then the resolved provider's own [providers.<name>].default_model, then the global top-level default_model in config.toml, then a baked-in fallback. So a provider-scoped default_model beats the global one — an agent pinned to a custom endpoint with no model: of its own gets that provider's model, not the global default (which the custom endpoint would typically reject as unknown).

Note. Workflow steps inherit the provider/model/auth of the agent they invoke, and a step can override them — so the same agent can run on different models in different workflows without editing the agent file.

Authentication

Under the hood rupu has three neutral auth modes: api-key, sso and device. The SSO mode resolves to the right OAuth flow per vendor (a localhost browser callback for Anthropic / OpenAI / Gemini / GitLab, or a GitHub device code for Copilot and GitHub), and device is the login for a machine with no browser.

SSO access tokens (typically ~1 hour) are refreshed pre-emptively — the resolver refreshes when expires_at - now < 60s on a credential read, using the stored refresh token. There is no automatic fall-back from SSO to API key: if you chose SSO, a refresh failure names the account and points you back at rupu auth login.

OAuth refresh across processes

Several rupu processes — a cp serve, a workflow, a second terminal — can share one login safely. Logins, logouts and every token refresh hold a lock file beside the store (auth.json.lock):

  • One refresh at a time. A process that finds a token near expiry takes the lock, re-reads the stored credential, and only asks the provider for a new token if another process hasn't already done so. New tokens are written to a temporary file and renamed into place, so a reader never sees a half-written file.
  • Bounded waits. Waiting for the lock gives up after 30 seconds with an error naming the lock file, rather than hanging.
  • Rotated tokens are not lost. If a refreshed token can't be saved (read-only directory, full disk), the process keeps using it in memory, says so on stderr, and retries the write later. On exit — including SIGTERM — rupu waits up to 10 seconds for a credential write still in flight.

How credentials are stored

There is one credential backend: a JSON file. The OS keychain backend was retired — a bare CLI binary's keychain access requirement is cdhash-bound, so every rebuild invalidated it and the next read failed silently ("my credentials vanished after an update"). Peer CLIs — gh, aws, gcloud, kubectl, terraform — store credentials in files for the same reason.

  • The store — ~/.rupu/auth.json, mode 0600. A flat JSON object of <provider>/<mode> keys (e.g. anthropic/api-key, gemini/sso) to secret payloads. Permissions are re-applied to 0600 on every write, so a previously loose file is tightened the next time you log in; a wider mode on read logs a warning rather than refusing — refusing would block recovery on a misconfigured machine.
  • Plaintext, so the file mode is the protection. Secrets are not encrypted at rest and are never printed back by rupu auth status. Keep ~/.rupu out of backups you would not trust with an API key.
  • Relocatable — RUPU_AUTH_FILE and RUPU_HOME. RUPU_AUTH_FILE points at an exact file; RUPU_HOME moves the whole rupu directory ($RUPU_HOME/auth.json). These select a path — nothing selects a backend any more, and the old RUPU_AUTH_BACKEND variable no longer diverts storage.
  • Global only. auth.json is never read from a project directory — credentials live at the user level.
Breaking change — upgrading from a keychain build. Credentials written by an older rupu are still sitting in the macOS keychain and are no longer read. rupu auth login probes for them (read-only, it never reads a secret or prompts for access) and prints a notice naming the affected providers — built-ins and your own openai-compatible ones alike. The remedy is to re-authenticate: rupu auth login --provider <name> --mode api-key|sso, which writes to the file store. Nothing is imported or deleted automatically; the old entries stay untouched and you can clear each one with security delete-generic-password -s rupu -a <account>.

Device login (--mode device)

rupu auth login --account <name> --mode device

For a machine with no browser (a server, a VM, an SSH session): rupu prints what to open, you complete the login in a browser on any other machine, and rupu stores the result. The credential is the same one --mode sso stores and lands in the account's sso entry, so rupu auth status shows sso, an agent's auth: sso picks it, it refreshes like any SSO token, and rupu auth logout --mode device removes it (the same entry as --mode sso).

Vendors with a device login:

  • anthropic: Claude Code's paste-the-code login (below).
  • openai: Codex CLI's device auth (below).
  • gemini: Gemini CLI's paste-the-code login (below).
  • copilot, github: the GitHub device-code flow, the same flow as their --mode sso.
  • gitlab: GitLab's device authorization grant (below).

Any other vendor refuses with <kind> has no device login; use --mode api-key (an openai-compatible account is refused earlier, by openai-compatible providers only support --mode api-key). --mode sso itself, on a Linux machine with neither DISPLAY nor BROWSER set, refuses before it binds a listener with SSO requires a desktop browser. Run with --mode device to log in from any browser, or --mode api-key.; rupu never switches modes on its own.

What you see, and where. Every prompt and progress line (the URL, the code, Waiting for approval…, Paste the code the page shows:) goes to stderr. The only line on stdout is the result, rupu: stored <account> sso credential, so a script can capture stdout and still show the operator the instructions. The paste prompt (Anthropic, Gemini) reads one line from stdin whether or not stdin is a terminal, so the code can arrive through a pipe or a here-string as well as by typing; it has to be the code the page shows for the URL this run printed, since each run makes a new one. A pasted or entered code is never echoed back or logged.

Stored as sso. device is a way to log in, not a storage slot. The credential lands in the account's sso entry of ~/.rupu/auth.json, so everything downstream treats it as an SSO login: rupu auth status shows sso, an agent's auth: sso picks it (and the default precedence prefers it over an API key), it refreshes through the same per-vendor path as a browser login, and rupu auth logout --account <name> --mode device removes the same entry as --mode sso.

Polling (GitHub, Copilot, GitLab). These are RFC 8628 device-code flows. rupu polls the token endpoint at the interval the vendor's reply names, else every 5 seconds, never faster than once a second. A slow_down reply adds 5 seconds to the interval unless it names a new one; authorization_pending keeps polling. The wait ends at the server's expires_in (GitLab's codes expire after five minutes, GitHub's after fifteen), or after 15 minutes when the reply names none, with device-code flow timed out; any other error (expired_token, access_denied) ends the login with device-code flow error: <error>. OpenAI's flow is not RFC 8628 (see OpenAI below): it polls at the interval OpenAI's reply names (5 seconds when it names none), treats a 403 or 404 while polling as "not yet", and gives up 15 minutes after the first poll with device login timed out.

Anthropic

rupu auth login --account anthropic --mode device
# Open this URL in any browser and sign in:
#
#   https://claude.ai/oauth/authorize?…
#
# Paste the code the page shows: <paste, then Enter>
# rupu: stored anthropic sso credential
  1. Open the URL rupu prints in a browser on any machine and sign in with your Claude account (the login Claude Code runs when it can't reach a browser).
  2. The page (platform.claude.com/oauth/code/callback) shows a code of the form code#state. Copy all of it and paste it at the prompt of the run that printed the URL (each run makes a new one); the page's full address, or the code alone, is accepted too.
  3. rupu exchanges the code for tokens and stores them as --mode sso does.

A pasted state that isn't this login's ends it with pasted state does not match this login; start again. The code expires within minutes and works once: if the exchange fails, rupu shows Anthropic's message and stores nothing; run the command again for a new URL.

Gemini

rupu auth login --account gemini --mode device
# Open this URL in any browser and sign in:
#
#   https://accounts.google.com/o/oauth2/v2/auth?…
#
# Paste the code the page shows: <paste, then Enter>
# rupu: stored gemini sso credential
  1. Open the URL rupu prints in a browser on any machine and sign in with your Google account (the login Gemini CLI runs with NO_BROWSER set).
  2. Google's page (codeassist.google.com/authcode) shows an authorization code. Paste it at the prompt of the run that printed the URL (each run makes a new one); the page's full address is accepted too.
  3. rupu exchanges the code for tokens, stores them as --mode sso does and sets up the account's Code Assist project (see Gemini below).

The URL asks Google to show its consent screen on every device login, so that Google always issues a refresh token (without it, an account that had already consented once would get a one-hour token). If Google still returns no refresh token, rupu says Google returned no refresh token. Revoke "Gemini CLI" at https://myaccount.google.com/permissions and log in again, or use --mode api-key and stores nothing. The code works once and expires within minutes; if the exchange fails, run the command again for a new URL.

OpenAI

rupu auth login --account openai --mode device
# Visit https://auth.openai.com/codex/device and enter code: ABCD-1234
# Only continue if you started this login yourself. The code expires in 15 minutes.
# Waiting for approval…
# rupu: stored openai sso credential
  1. rupu asks auth.openai.com for a one-time code (the login Codex CLI runs for codex login --device-auth).
  2. Open https://auth.openai.com/codex/device in a browser on any machine, sign in with your ChatGPT account and enter the code.
  3. rupu polls until you approve it, then exchanges the approval for tokens and stores them as --mode sso does. A login nobody approves ends after 15 minutes with device login timed out; a reply other than "approved" or "not yet" (a 403 or 404) ends it with device login failed with status <code>.

Device login is off by default for a ChatGPT account. If rupu says device login is not enabled for this ChatGPT account. Turn it on in ChatGPT settings → Security (a workspace admin does it under workspace permissions), then retry; or log in from a desktop with --mode sso (OpenAI answers the code request with a 404), do that and retry.

Only enter a code from a login you started yourself: whoever started the login gets the account the code is approved for.

GitLab

rupu auth login --account gitlab --mode device
# Visit https://gitlab.com/oauth/device and enter code: 0A44L90H
# Waiting for approval…
# rupu: stored gitlab sso credential
  1. rupu asks the account's instance (POST <instance>/oauth/authorize_device) for a code, as the application --mode sso uses: glab's on gitlab.com, else the [scm.<account>] oauth_client_id the instance needs (see Integrations).
  2. Open the URL rupu prints in a browser on any machine, sign in and enter the code.
  3. rupu polls until you approve it and stores the tokens as --mode sso does; they refresh the same way. A code nobody approves expires after five minutes.

The device grant needs GitLab 17.9 or later. An older instance answers with a 404, and rupu says this GitLab does not offer device login (it needs GitLab 17.9 or later): log in from a desktop with --mode sso, or use --mode api-key with a personal access token.

GitHub and Copilot

For GitHub (the SCM account) and Copilot, --mode device runs exactly the same GitHub device-code flow as their --mode sso (rupu prints Visit https://github.com/login/device and enter code: … and polls until you approve) and stores the same sso credential; for these two vendors the mode words are interchangeable. The flow needs no browser on the machine running rupu, so it works headless and over SSH. It follows the polling rules above (GitHub's codes expire after fifteen minutes).

rupu auth login --provider github --mode device
rupu auth login --provider copilot --mode device

The rupu auth CLI

The rupu auth subcommand manages stored credentials:

  • rupu auth login — store credentials for an account (--account / --provider, --kind the first time a new account name is used, --mode api-key|sso|device, optional --key). Also where the stranded-keychain notice fires.
  • rupu auth logout — remove a stored credential (--account [--mode], or --all [--yes]).
  • rupu auth status — show which accounts have an API key or SSO credential stored; never prints secrets.
  • rupu auth backend — report where credentials live. It no longer switches anything: --use file is the only accepted value (and is already in effect), and --use keychain fails with an explanation rather than silently writing to a file you did not choose.
# API key: pass it inline, or pipe it on stdin
rupu auth login --provider anthropic --mode api-key --key sk-ant-XXX
echo -n "$KEY" | rupu auth login --provider openai --mode api-key

# SSO (browser callback or device code, chosen per provider)
rupu auth login --provider copilot --mode sso

# No browser on this machine: finish the login from a browser elsewhere
rupu auth login --provider openai --mode device

# A second account of a vendor you already use
rupu auth login --account openai-lab --kind openai --mode api-key

# Inspect and clean up
rupu auth status
rupu auth logout --provider gemini --mode sso
rupu auth logout --all --yes

# Report where credentials live (there is only one backend)
rupu auth backend

# Store the file somewhere else
export RUPU_AUTH_FILE=/secure/volume/rupu-auth.json

Models are discovered separately with rupu models: rupu models list shows the catalog for the built-in vendors and every declared account (with a --provider filter that also takes an account name), including each model's input limit, output cap, source and fetch age; rupu models refresh re-fetches the live lists, per account, with that account's own credential. Every run resolves its model's real input limit and output cap — agent frontmatter, then [[providers.<name>.models]], then the live list — and records where each came from. See Recovery & reliability → Model limits discovery.

Model discovery notes

  • OpenAI with an API key also sends the key, as a Bearer token, to chatgpt.com/backend-api/codex/models (the only endpoint beyond api.openai.com) to read the Codex catalog's limits. That first call has its own 3-second timeout, so the fallback still fits the 10-second listing budget: if it fails, times out or lists nothing usable, rupu falls back to the ids-only GET /v1/models.
  • The Codex catalog is versioned. rupu requests it as /backend-api/codex/models?client_version=0.166.0. The server filters the catalog by each model's minimum client version, so the pin is protocol compatibility with the Codex CLI release rupu verified against, not rupu's own version, and needs no Codex installation; an older pin (0.50.0) returned an empty catalog even for a valid login.
  • Hidden models are dropped. A Codex catalog entry whose visibility is anything but list is left out (an entry with no visibility field is kept, as the public /v1/models and gateways have none), and with an API key an entry marked supported_in_api: false is left out too. A model that works in your ChatGPT app but that the catalog hides therefore never appears in rupu models list --provider openai; to use it, add it under [[providers.openai.models]] (the id is still sent as written) and declare its limits there.
  • Gemini CLI / Code Assist login exposes no model limits. Declare them yourself with [[providers.gemini.models]] (or pin contextWindowTokens / maxTokens on the agent); with that login, rupu models refresh --provider gemini reports that there is no listing rather than pretending to fetch one.

In the control plane. Settings → Models lists every provider's cached models, with a Refetch button per provider and a Refetch all button, backed by GET /api/models and POST /api/models/refresh (body {} for all providers, or {"provider": "<name>"} for one); it refreshes the control-plane machine's cache only. Reading the responses: GET /api/models reads the cache only (no network) and answers one entry per provider, {"provider", "fetched_at", "stale", "models": [{"id", "input_tokens", "output_tokens", "source"}]}. stale: true means the cached list is older than its hour; fetched_at: null together with stale: false means the provider was never fetched (nothing is cached, so nothing is stale), not that it is fresh. POST /api/models/refresh answers 200 whenever the refresh ran, with one {"provider", "ok", "count", "error"?} per provider targeted; a provider that could not be refreshed is reported as ok: false with its error inside that 200, so check each provider's ok, not the status code. A body naming an unknown provider, or a malformed body, is a 400; an empty body refreshes every provider. Routes: HTTP API.

Per-provider notes

Anthropic

Console API keys start with sk-ant- and are shown only once — copy at creation. SSO authenticates via Claude.ai's OAuth (claude.ai/oauth/authorize), good for Claude Pro subscribers. Access tokens last ~1 hour and refresh automatically. On a machine with no browser, --mode device prints the same authorize URL and waits for the code#state the callback page shows; see Device login.

Prompt caching is on by default. Every Anthropic request carries at most two cache_control breakpoints (5-minute TTL): one caches the tool definitions and system prompt, the other sits on the end of the conversation and moves forward each turn, so prior turns are re-read from the cache. Cache reads and writes show up in usage as cached_tokens / cache_write_tokens and are priced at the model's cache rates. Turn it off per account with prompt_cache = false under [providers.<name>] (for a gateway that rejects cache_control), or per agent with anthropicPromptCache: false.

On API-key auth, rupu also opts current Claude models into Anthropic's server-side fallback — see Recovery & reliability.

OpenAI

Two paths hit different endpoints: a Platform API key (sk-...) targets api.openai.com/v1/responses and is billed via OpenAI; ChatGPT SSO targets the ChatGPT backend and is covered by a Plus/Pro subscription. rupu detects the chatgpt_account_id claim and routes accordingly. Org-scoped keys need org_id in config. Only the newer Responses API is supported — pre-Responses models won't work. Without a browser, --mode device runs Codex CLI's device auth and stores the same ChatGPT credential; it has to be enabled on the ChatGPT account first (see Device login).

OpenAI Daybreak cyber access

OpenAI's Daybreak program gates its cyber-capable models (gpt-5.6-cyber, for example) behind an access program the caller selects per request. rupu selects it with cyber, which it sends on the Responses API request body as access_programs: { cyber: <value> }:

  • standard: the ordinary access tier (no cyber program).
  • daybreak_blue: the Daybreak defensive program.
  • daybreak_red: the Daybreak offensive program.

Setting cyber selects a program; it does not grant access. Your organization and project must already be approved for it, and the value must match the model. rupu passes the value through unchanged, so a wrong pairing comes back as OpenAI's invalid_access_program error on the request rather than a rupu error.

Which logins carry it. Both. The request body is built the same way for the platform API (api.openai.com/v1/responses, API key) and the ChatGPT endpoint (chatgpt.com/backend-api/codex/responses, SSO or device login), so the program rides on either; whether OpenAI honours it is the approval of the account the request authenticates as. Only the OpenAI client sends it: an agent on provider: openai (or an account declared with kind = "openai", "openai_codex" or "codex", all the same client). Every other provider ignores the value.

Organization and project. With an API key, [providers.openai] org_id is sent as the OpenAI-Organization header on the platform API only (never on the ChatGPT endpoint, which is scoped by the account). rupu sends no OpenAI-Project header, so the project is the one the API key belongs to: create the key inside the project OpenAI approved for the program. With a ChatGPT login there is no organization or project header at all; the approval is the ChatGPT account's.

Where to set it, highest first.

  1. rupu run <agent> --cyber <program> overrides everything for that run. rupu run --continue <id> restores it with the rest of the original command; a --cyber given on the continue replaces it.
  2. The agent's cyber: frontmatter (Agents). An unknown value there is a parse error: the agent does not load.
  3. A cyber on the [[providers.openai.models]] entry whose id is the run's model (Configuration). An unknown value there is ignored with a warning in the log, not an error.
---
name: exploit-verifier
provider: openai
model: gpt-5.6-cyber
cyber: daybreak_red
---
rupu run exploit-verifier --cyber daybreak_red

Behaviour notes.

  • A fallback hop keeps the program only while the model stays the same; a hop to another model or provider drops it, since the right value is model-specific. A chain entry that names another model therefore runs without a program.
  • The compaction summariser call never carries it: only the turn requests do.
  • A session freezes the program from the agent at rupu session start and sends it on every turn; a session settings override of the provider or model clears it (the override's model may not take the same program). rupu session start has no --cyber flag.
  • --cyber is not sent to remote placed units (host: / distribute:): the coordinator's flag stays on the coordinator. A placed unit runs the agent file installed on that host, so put cyber: in that file (or in that host's config) to run it under a program.
  • provider: openai-codex (with a hyphen) is only the display id rupu uses in transcripts and pricing, not a built-in provider name; it works only as a declared account, [providers.openai-codex] kind = "openai_codex", logged in under that name.

Gemini

Two different Google APIs sit behind one gemini provider:

  • API key (--mode api-key) — a Google AI Studio key (AIzaSy…). AI Studio publishes a model list with per-model token limits.
  • SSO (--mode sso) — the Gemini CLI / Antigravity Google sign-in, used against Cloud Code Assist, the backend the Gemini CLI talks to. No Vertex AI setup is involved, and the region key is unused. Code Assist has no model listing, so declare limits in [[providers.gemini.models]] (or pin them on the agent).

Code Assist project. Every Code Assist request names the Google Cloud project Google meters the account's usage against. rupu sets it up the way the Gemini CLI does — asking Google for the account's tier and project, onboarding a new free-tier account (Google provisions a managed project) — once at rupu auth login --provider gemini --mode sso, and stores the result in the credential so later runs skip the setup. A paid (standard-tier) account needs its own project: set GOOGLE_CLOUD_PROJECT (or GOOGLE_CLOUD_PROJECT_ID) to its project ID. If no project can be found, the request fails before anything is sent, with an error naming GOOGLE_CLOUD_PROJECT and the API-key alternative.

Without a browser, rupu auth login --provider gemini --mode device prints a Google sign-in URL, reads the code Google's page (codeassist.google.com/authcode) shows from stdin, stores the result as the account's sso credential exactly as --mode sso does, and sets up the Code Assist project afterwards. The URL carries prompt=consent and access_type=offline so Google always returns a refresh token; if it returns none, nothing is stored. See Device login.

Copilot

Requires a paid Copilot Pro / Business / Enterprise subscription — a free GitHub account can't invoke the API even with a valid token. The simplest path is a GitHub PAT (ghp_...), or pick it up from GITHUB_TOKEN when --key is omitted. The SSO flow is the same device-code flow gh auth login uses: rupu prints Visit https://github.com/login/device and enter code: ABCD-1234, you authorize from any browser anywhere (no browser is needed on the machine running rupu, so it works headless and over SSH), and rupu polls until you do, then exchanges the GitHub token for a Copilot API token. rupu auth login --provider copilot --mode device runs exactly the same flow and stores the same sso credential; for Copilot and GitHub the two mode words are interchangeable. The other vendors have their own device logins now (--mode device for Anthropic, OpenAI, Gemini and GitLab), so this is no longer the only headless SSO; see Device login for what each prints and how long it waits. The exchanged Copilot token expires faster than the GitHub PAT; rupu re-mints it internally.

GitHub and GitLab (SCM accounts)

Both SCM vendors share the credential store and the same three mode words. GitHub logs in with --mode api-key (a personal access token), --mode sso (the device-code flow above) or --mode device (that same flow under the mode word every other vendor's headless login uses); the credential is stored as the account's sso entry either way. GitLab logs in with a personal access token, glab's PKCE browser login (--mode sso) or GitLab's device authorization grant (--mode device, GitLab 17.9 or later); a self-managed instance needs [scm.<account>] base_url and oauth_client_id. Scopes, the [scm.<account>] declaration and routing are on Integrations; the polling rules are under Device login.

rupu auth login --provider github --mode device
rupu auth login --provider gitlab --mode device

Bring your own provider (OpenAI-compatible)

The four built-ins are not the boundary. With the openai-compatible provider kind you can register any HTTP server that speaks the OpenAI /v1/chat/completions API as a named provider, then use it from agents exactly like a built-in — and mix it with the built-ins in one workflow. That covers:

  • Local models — vLLM, llama.cpp, or Ollama running on your own machine or a GPU box.
  • Gateways & aggregators — OpenRouter, Together, Groq, Fireworks, and similar OpenAI-shaped endpoints.
  • Private / enterprise endpoints — a hosted enterprise model service or an internal company gateway.

Authentication is a single static Bearer API key per provider — there is no SSO flow for openai-compatible providers. The model catalog is what you declare in config plus whatever the server's /v1/models reports, which rupu models refresh fetches with the account's key.

Configure it

Add a [providers.<name>] table to ~/.rupu/config.toml with kind = "openai-compatible". base_url and default_model are required; stream is optional (defaults to true; set false for servers without an SSE endpoint). Add one [[providers.<name>.models]] block per private or fine-tuned model you want to select.

default_provider = "gpubox"

[providers.gpubox]
kind = "openai-compatible"
base_url = "http://gpu-box.internal:8000"
default_model = "acme/coder-32b"
stream = true   # set false if the server has no SSE endpoint

  [[providers.gpubox.models]]
  id = "acme/coder-32b"
  context_window = 131072
  max_output = 8192

base_url may include or omit a trailing /v1 — rupu normalises both to <root>/v1/chat/completions. Each [[providers.<name>.models]] entry requires id; context_window and max_output are optional. When omitted, rupu reads max_model_len from the server's /v1/models; if that's missing too, the limits are unknown and the run says so — there are no made-up defaults. Name the provider anything you like — gpubox, vllm, together — except a reserved built-in name (anthropic, openai, gemini, copilot); rupu rejects the config otherwise.

Authenticate

Supply the static Bearer key with rupu auth login (stored in ~/.rupu/auth.json under <name>/api-key, same as the built-ins), or — for CI and ephemeral environments — set the env var RUPU_<UPPERCASED_PROVIDER_NAME>_API_KEY and rupu reads it automatically.

# Interactive prompt (the key is not echoed), or pipe it on stdin
rupu auth login --provider gpubox --mode api-key

# Or set the env var directly — pattern: RUPU_<PROVIDER>_API_KEY
export RUPU_GPUBOX_API_KEY=sk-...

Use it from an agent

Point an agent at the provider by name; the model: can be any id the endpoint serves, including the custom [[providers.<name>.models]] entries that make private or fine-tuned models selectable.

---
name: local-codereview
description: Code review on a self-hosted model.
provider: gpubox
model: acme/coder-32b
---

You review code changes for correctness, style, and missing tests.

Then run it like any other agent, and confirm the custom catalog with rupu models list --provider gpubox (entries show source custom):

rupu run local-codereview

Usage & pricing

Every LLM call a run makes — every turn, compaction summary, retry, dispatched sub-agent and fan-out unit, in-flight or cancelled — is appended to the run's own usage ledger (usage.jsonl next to the run record) as it happens. That ledger is the single definition of a run's usage: the control plane shows a running run's tokens and cost within seconds of each turn (runs on SSH and tunnel hosts too; bucket hosts follow their poll interval), and rupu usage, rupu workflow runs and the CLI live view all fold the same rows.

Tokens become dollars through [pricing]: a user override, then a built-in table of each vendor's standard-tier list rates, then a per-agent fallback for endpoints with no public price. Named accounts price through their kind, with an account-level override beating the vendor one. Anthropic cache reads and writes are priced at their own rates.

[pricing.anthropic."claude-sonnet-4-6"]
input_per_mtok = 3.0
output_per_mtok = 15.0
cached_input_per_mtok = 0.30   # optional
cache_write_per_mtok = 3.75    # optional

[pricing.agents.local-codereview]     # an endpoint with no public price
input_per_mtok = 0.5
output_per_mtok = 1.5
