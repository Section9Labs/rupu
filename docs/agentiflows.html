Agentiflows

An agentiflow is a goal-directed, budget-bounded fleet run. You state measurable goals, a budget, a pool of agents and workflows, and an authorized scope; a lead agent decides how to reach the goals — dispatching agents, running or generating workflows, and coordinating them over a shared board — while deterministic code holds the budget and the stop button.

What is an agentiflow

A workflow is structure you wrote in advance. An autoflow picks up work items and runs a pre-written workflow on each. Neither can compose new structure in response to what it finds, coordinate a live fleet, or stop itself when a measurable goal is met. That's what an agentiflow is for: open-ended work like “review this service and verify every real injection flaw”, where the plan has to change as the evidence comes in.

Who decides the stepsWhen it stops
WorkflowYou, in YAML, ahead of timeWhen the last step finishes
AutoflowYou, in YAML; the runtime picks which item to run it onPer item, when its workflow finishes
AgentiflowA lead agent, round by round, from a fixed poolGoals met, coverage reached, budget or ceiling hit, or an operator stop

The design is deliberately split. A deterministic envelope owns the loop: rounds, the budget, the stop conditions and the operator's steering queue. Inside each round the lead runs as an ordinary rupu agent with a large turn budget, so the work is fully agentic — but code, never the model, decides when the money is spent and when the run is over.

How a run works

An agentiflow runs in rounds. At the start of every round the envelope evaluates each stop condition against the evidence the fleet has written so far — findings, assets and coverage in the run's pooled coverage scope, plus the metered spend — and either stops the run or hands the lead a digest: where every goal stands, the coverage fraction, the budget stage, any operator steering that arrived since the last round, and any non-fatal warnings. Round 0 opens with the mission — each goal's objective, in order — and the authorized scope: scope.mode and one line per scope.roots entry, its kind followed by its coordinates (network:host host=10.0.0.5).

The lead then takes up to round.lead_max_turns agentic turns (default 50). It reads the roster, launches units, joins them, posts to the board and checks goal status. When its turns end, the round ends, and the envelope evaluates again. “Done” is never the lead's say-so: a goal is met only when the evidence on disk satisfies its predicate, and an evaluation that fails counts as not met. The conditions are checked in the order below; the first match wins.

Stop reasonFires when
goals_metAt least one goal is required, and every required goal's predicate holds over the pooled evidence.
coverage_reachedThe coverage: fraction reaches its reach.
budget_exhausted:<dimension>A budget dimension — usd, tokens, rounds or wall_clock — hits its cap. The first to trip is named.
operator_stopYou asked it to stop (rupu agentiflow stop); a hard stop is recorded as operator_stop:now.
ceilingThe hard round.ceiling on rounds or wall-clock time is reached.

Writing an agentiflow

An agentiflow is one YAML file. rupu agentiflow run <name> loads <project>/.rupu/agentiflows/<name>.yaml, falling back to ~/.rupu/agentiflows/<name>.yaml (a project file shadows the global one). Every block rejects unknown keys, and the whole file is validated against its engagement profiles before anything starts — a goal that could never be met is a load error, not a run that burns its budget. 

# .rupu/agentiflows/ledger-review.yaml
name: ledger-review
description: Coordinated pre-release review of the ledger service.
lead: review-lead                    # must be in pool.agents
engagement_profiles: [code]

goals:
  - id: verified-sqli
    objective: "Find and independently verify two SQL injection flaws."
    target:
      findings: { classification: CWE-89 }
      count_gte: 2
      verified: true
      verify_check: with_poc          # confirmed AND an artifact on the report
    verify_with: finding-verifier       # only this pool agent's verdict counts
  - id: core-file-reviewed
    objective: "Bring the ledger core module to reviewed depth."
    required: false                  # reported, but doesn't block goals_met
    target:
      asset: { kind: "code:file", locator: { path: src/ledger/core.rs } }
      depth_at_least: reviewed

coverage: { reach: 0.9, depth: reviewed, kinds: [file] }

budget:
  usd: 20
  tokens: 4000000
  wall_clock: "2h"
  rounds: 10
  soft_at: 0.8                     # converge once any dimension passes 80%

scope:
  authorized: true
  roots:
    - { kind: "code:repo", path: "." }

pool:
  agents: [review-lead, code-reviewer, security-reviewer, finding-verifier]
  workflows: [deep-review]               # or: all

round:
  lead_max_turns: 80
  ceiling: { rounds: 12, wall_clock: "3h" }
FieldRequiredMeaning
nameyesThe run's definition name.
leadyesThe agent that runs each round. Must be listed in pool.agents.
engagement_profilesyesThe engagement profile set (code, web, network, binary, …) that defines the asset kinds, coverage ladders and finding classifications the goals refer to. An unknown profile id fails the load. It's carried to every unit the lead launches. See Engagement profiles.
goalsone of goals / coverageMeasurable targets. A findings target counts findings (optionally by classification, e.g. CWE-89) and needs count_gte. An asset target names a profile-namespaced kind plus a locator and needs depth_at_least, a rung of that profile's coverage ladder. required defaults to true.
coverageone of goals / coverageAn engagement-wide stop: reach in (0, 1], an optional depth rung, and optional kinds to measure. Validated to be reachable.
budgetnousd, tokens, wall_clock (Ns/Nm/Nh/Nd), rounds, and soft_at (default 0.8). Every field is optional; an unset one never stops the run. See Budgets.
scopeyesauthorized: true is mandatory — it's your statement that the fleet may act unattended. Optional roots name root asset kinds of an active profile (code:repo, network:host, web:site) with their coordinates; they are validated and listed, with mode, in the lead’s opening-round prompt as the authorized targets.
poolyesThe fixed set of agents and workflows (a list, or all) the lead may launch. The lead never invents new fleet agents.
roundnolead_max_turns per round (default 50, at least 1) and a hard ceiling on rounds / wall_clock.
Agentiflows run unattended. The lead runs without approval prompts and every unit starts in bypass mode, in the directory you launch from. Scope roots are typed, validated and shown to the lead, but rupu does not enforce scope in code: nothing stops an agent from reaching beyond them, so put hard constraints in the goal objectives too. Only put agents in the pool that you're happy to run unattended.

The lead's toolbox

The lead is a normal agent file (Markdown + YAML) — its system prompt is yours to write. It gets the tools its own tools: lists, report_finding (plus asset_mark under an engagement profile), and these fleet tools, always on:

ToolWhat it does
dispatchStart a pool agent as a unit with a prompt. Refused for an agent outside pool.agents. Returns a handle.
run_workflowStart a pool workflow as a unit, with inputs. Vetted before launch: it must be in the pool, dispatch only pool agents, have no approval gates or host:/distribute: placement, and its inputs must resolve.
generate_workflowAuthor a new workflow from a description, vet it the same way, save it under the run's generated/ directory, and run it as a unit. Offered when a generation provider with an API credential is available.
joinWait for a unit to finish (default 300 s, at most 3600 s per call) and return its outcome.
goal.status · coverage.status · budget.statusWhere the goals, coverage and spend stand right now — including, for a verification-gated goal, how many matching findings are still awaiting a verdict.
agents.list · agents.get · workflows.list · workflows.get · catalog.searchRead the roster: what each pool agent and workflow is for, its tools, its inputs.
board.directive · board.retractSet (or lift) a standing directive every participant sees on each turn.
board.claim · board.release · board.post · board.read · msg.sendThe shared coordination tools — the same ones every agent unit gets.

Dispatch is non-blocking: the lead can start several units in one turn, keep working, and join them later. Each lead turn also carries its inbox, the standing directives and a short index of the pool, so it knows what it can start without spending a turn on agents.list.

Units, the board and mailboxes

Every unit runs as its own process — an agent unit is a rupu run, a workflow unit a rupu workflow run, both in bypass mode — attached to the agentiflow with a unique participant id like code-reviewer#2. Units file their findings and assets into the run's pooled coverage scope, which is exactly where the envelope looks when it evaluates the goals. Agent units get the board and mailbox tools below. Starting units is the lead's job alone; an agent's own in-process dispatch_agent sub-agents still work.

Participants coordinate through a file-backed store in the run directory:

  • Claims. board.claim takes a one-hour lease on a piece of work (say, a file or a component) so two units don't duplicate it; board.release gives it back.
  • Posts. board.post appends an observation, question, answer, vote or note — optionally addressed to one participant or role. board.read reads them back.
  • Directives. Standing instructions from the lead, shown to every participant until retracted.
  • Mailboxes. msg.send delivers to a participant id, a role, parent, lead, or broadcast (each participant sees a broadcast once).

Nobody spends a turn polling for messages. Before each model call, a pre-turn collector drains the participant's inbox and the live directives into its context, so news arrives at the next loop iteration on its own. Messaging is fire-and-forget; there are no blocking waits between agents.

Budgets and metering

Spend is metered from the usage ledgers (usage.jsonl) of the lead and of every unit it launched, folded into per-model and total token counts and priced through your layered [pricing] config. Each budget dimension is evaluated as a fraction of its cap:

  • Soft — once any set dimension passes soft_at, the digest tells the lead to converge: wrap up and bank the highest-value work rather than open new lines of inquiry.
  • Hard — the first dimension to reach its cap stops the run before the lead is consulted again. A zero cap is exhausted immediately, never “unlimited”.

budget.usd is enforced when the lead's model has a price; if it doesn't, the dollar cap is dropped with a warning at launch and the other dimensions still apply — add a [pricing] entry for the model to enforce it. The running spend is written to the run record after every round, so status and the control plane show it live.

Known gap. Sub-agents that a unit launches through dispatch_agent don't write a usage ledger yet, so their spend isn't counted. A unit that delegates heavily makes budget.usd / budget.tokens trip later than the true spend — keep a wall_clock or rounds cap as a backstop.

Verified goals

Verification is opt-in per goal. With verified: true on a findings target, only findings that carry a confirmed verdict from a different run than the one that filed them count. Add verify_with: <agent> to require that verdict come from one named pool agent, and verify_check: with_poc to also require at least one artifact (a proof of concept) on the finding's report. verify_with alone turns verification on.

Verdicts are recorded with the finding.verify tool — confirmed, disputed or inconclusive. It is only registered for an agent that lists finding.verify in its tools:, it refuses a finding filed by the same run, and it needs a finding with a full report — so the agents that file findings should use findingsProfile: full. goal.status shows the lead how many matches are still unverified, so it knows to dispatch the verifier. See Findings for the report format.

Running and steering

CommandWhat it does
rupu agentiflow run <name>Validate and run in the foreground until a stop. --detach starts it in its own process group, returns once the run has started, and prints the run id; a run that fails to start reports why.
rupu agentiflow listEvery run, newest first.
rupu agentiflow status <id>One run: goals, budget, rounds, and why it stopped.
rupu agentiflow attach <id>Follow the run's event log and the lead's transcript for the round in progress. --no-follow (--once) prints what's recorded and returns. Ctrl-C leaves the run going.
rupu agentiflow send <id> "<message>"Steer the lead. Delivered at the next round boundary; with --now the lead's current round is cut short at a safe point and the message is delivered at once.
rupu agentiflow stop <id>Graceful stop at the next round boundary, units included. --now signals the coordinator and every running unit immediately (SIGKILL after a short grace) and records the run as failed (operator_stop:now).
rupu agentiflow serveReap orphans: a run whose coordinator died is recorded as failed and its units are stopped. Runs until SIGTERM / Ctrl-C.

Run ids look like af_…; every command accepts the full id, the compact form list prints, or a unique prefix or suffix.

# start in the background and watch it
rupu agentiflow run ledger-review --detach
rupu agentiflow attach af_01K…

# redirect the lead mid-flight
rupu agentiflow send af_01K… "Skip the CLI wrappers; focus on the query builders."

# wind it down
rupu agentiflow stop af_01K…

The run directory

Each run lives under ~/.rupu/agentiflows/af_<id>/:

agentiflow.json            # the run record: status, live spend, stop reason
agentiflow.yaml            # the definition it started from
events.jsonl               # append-only event log
usage.jsonl                # the lead's usage ledger
lead/transcript.r<N>.jsonl # the lead's transcript for round N
steering/                  # queued operator messages
board/                     # posts, directives, claims
mailboxes/                 # per-participant inboxes + the broadcast log
units/<run id>/unit.json   # one record per unit
generated/                 # workflows the lead authored
detach.log                 # stderr of a --detach run

Orphan reaping

A coordinator that is killed outright would otherwise leave its run running and its detached units burning tokens. rupu cp serve sweeps for these on its own tick; on hosts that don't run the control plane, rupu agentiflow serve does the same job. 

[agentiflow]
serve_enabled = true          # whether `rupu agentiflow serve` runs
serve_interval_secs = 60      # seconds between its sweeps
reaper_enabled = true         # the reap itself, in serve and in cp serve

In the control plane

The control plane lists agentiflow runs under Runs → Agentiflows (status, stop reason, rounds, goals, spend) and gives each one a detail page with goals and budget usage in its header. A running run refreshes every 5 seconds.

TabShows
FlowThe run as a growing graph — the lead is the spine, round by round, and every unit it launched fans out as a branch and merges back into the next round — plus the fleet of units and their status. Earlier rounds collapse to a one-line summary (goals, budget, spend, unit count) so a long engagement stays compact; the latest round stays open, and the chevron or unit count toggles any round. An agent unit links to its transcript. A workflow unit is a full workflow run: it links to its own run graph (open flow →), and its chevron unfolds the workflow's steps beneath it, each with its agent and status, loaded only when you open it. A running sub-workflow's steps are a snapshot taken when you expand it; collapse and reopen to refresh.
AssetsEngagement assets (hosts, services, sites, routes, files) with their depth rung.
FindingsFindings filed by the lead and its units.
MessagesThe board — posts and the lead's directives — plus a Steer the lead box while the run is live, queued for the round boundary or sent mid-round. A message is accepted only while the run's coordinator process is alive (otherwise it would never be read): a run that died without finalizing still says running on disk until the orphan reaper closes it, and the page flags it.
TranscriptThe lead's transcript for the latest round, live while the run is going.
EventsThe raw event log, newest first.
Start and stop from the CLI. Runs are launched with rupu agentiflow run and ended with rupu agentiflow stop; the control plane observes and steers them. It reads runs on its own host, and units always run locally.
