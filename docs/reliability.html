Recovery & reliability

Long agent runs meet refusals, cut-off replies, rate limits, crashed terminals and killed processes. rupu classifies every reply into a typed outcome, works down a fixed recovery ladder before it gives up, and picks interrupted work up where it stopped instead of starting it over.

Response outcomes

A model's reply does not always give the agent what it needs: it can be cut off at the output limit, refused, blocked by a safety filter, empty, or stopped on a tool call that cannot be parsed. The provider can also fail the request outright. rupu classifies every reply and every provider error. A normal reply (an end_turn, tool_use or stop_sequence stop with usable text or a tool call) has no outcome; anything else gets a typed class with a severity:

ClassSeverityWhat happened
pause_turninfoThe provider paused a server-side tool loop and expects the conversation back to continue.
max_tokenserrorThe reply hit the output limit (and, when it cut a tool call off, which tool).
context_window_exceedederrorThe reply stopped because the context window is full.
refusalerrorThe model refused, with the provider's category when it gave one.
safetyerrorA safety filter blocked the reply.
malformed_tool_callerrorA tool call whose arguments could not be used.
incompleteerrorThe provider reported the reply as incomplete.
empty_replyerrorA normal stop with no text and no tool call.
unrecognized_stop / unreported_stopwarningAn unknown stop reason (the raw value is kept), or none at all.
provider_errorerrorThe request failed. A normalized error_class says how: rate_limited, overloaded, server, timeout, context_overflow, quota, not_found, policy, auth, permission, invalid_request, too_large or unrecognized.

Severity decides what happens next. A warning never fails a run: the reply is kept and the odd stop is recorded so it is visible. The one info outcome, pause_turn, is handled in place. An error enters the ladder.

Each outcome is written to the transcript as one outcome event, and every step taken to recover from it as a recovery event pointing back at it — so a transcript reads as a timeline. The CLI viewers (rupu transcript show, rupu watch, the live run view) print them as one-liners, and the control plane's transcript view shows them as severity-colored blocks:

✗ outcome   truncated · output limit
↺ recovery  rung 0 · continued 1/3
✗ outcome   refused · cyber
↺ recovery  rung 1 · fell back to anthropic/claude-sonnet-5-5

A failed workflow step, fan-out unit or run also records the outcome that caused it (its cause) on the run record, so a failure is stored as “refused” and not only as an error string.

The recovery ladder

When an error outcome occurs, rupu works down four rungs and stops at the first one that gets the run moving again:

OutcomeRung 0 (in place)BudgetFallback rungs
pause_turnSend the paused conversation back and join the continuation5none
max_tokensAsk the model to continue exactly where it stopped31 and 2
max_tokens mid tool callCompact, then retry at the model's full output cap (only when the cap had been lowered)11 and 2
context_window_exceededCompact the history, then continue31 and 2
refusal, safetynone01 and 2
malformed_tool_callSay what was wrong with the call and ask again21 and 2
empty_replySay the reply was empty and ask it to continue11 and 2
incompleteRetry the turn11 and 2
provider_error: rate limit, overload, server, timeout, overflowThe provider's own retry/backoff and overflow compaction run first—2 only
provider_error: quotanone02 only
provider_error: not_found, policynone01 and 2
provider_error: auth, permission, invalid request, too largenone — retrying elsewhere would not help0none
  • Budgets are per logical turn, and every action on every rung counts against one ceiling of 20 recovery actions per run. At the ceiling the run goes straight to rung 3.
  • Refused or retried partial replies are discarded: written to the transcript, but never sent back to the model.
  • Hops are sticky. Once a run moves to a fallback, later turns stay on it, and the fallback model is told that a previous attempt stopped and why.
  • A fallback that cannot be built (its provider is not configured, say) is recorded as skipped and the next one is tried.

Configuring fallbacks

A fallback chain is an ordered list of models, each with an optional provider. Declare it on an agent:

---
name: api-reviewer
provider: anthropic
model: claude-opus-5
fallbacks:
  - model: claude-sonnet-5-5     # same provider as the run → rung 1
  - provider: openai             # another provider → rung 2
    model: gpt-5
---

…or once, for every agent that declares none, in ~/.rupu/config.toml:

[recovery]
fallbacks = [
  { model = "claude-sonnet-5-5" },
  { provider = "openai", model = "gpt-5" },
]
server_side_fallback = true
  • Precedence. An agent's fallbacks: replaces [recovery].fallbacks — they are not merged — and fallbacks: [] means no fallbacks. With no chain anywhere, a run still gets rung 0 and then rung 3. Unknown keys in an entry are a load error, not a silent no-op.
  • Rungs. An entry without provider, or one on the provider the run started on, is a rung-1 candidate; every other entry is rung 2. Within a rung the chain order decides, and a model already tried is never offered again.
  • Credentials. A hop is built through the same credential resolver and [providers.<name>] table as the run's own provider. The agent's auth: mode applies only to a hop on the origin provider, and a hop does not inherit the agent's maxTokens / contextWindowTokens pins — its limits are discovered for the new model.
Data handling. A rung-2 hop sends the whole conversation — including file contents and tool output the agent has read — to a different vendor's API. Only put a provider in a chain when the run's data is allowed to go there.

Anthropic server-side fallback

Anthropic can fall back to another model on its own side when the requested model refuses, which saves a round trip. rupu opts in automatically for a fixed set of current Claude models (a [1m] suffix is ignored when matching) — on API-key auth only; a run on Claude.ai SSO never sends the opt-in. When the fallback answers, the turn proceeds normally and the transcript records the refusal as an outcome titled refused · served by <model>.

Turn it off with [recovery].server_side_fallback = false (default true). If an account or gateway rejects the opt-in, rupu stops sending it for that client, retries the request once, and writes a server_side_fallback_disabled notice — set the key to false for that account to skip the refused request on every run.

When nothing is left

When the ladder runs out, the run ends with status error and a message that names the next step, tailored to where the run started:

# rupu run <agent>
refused · cyber; no recovery left — continue with another model:
  rupu run api-reviewer --continue <run id> --model <model> [--provider <provider>]

# a workflow step
no recovery left — add fallbacks: to the agent or [recovery].fallbacks to try other models

# a session turn (the conversation is kept)
no recovery left — send another message to continue, or start a new session on another model

A failed step tolerated by continue_on_error: publishes an empty steps.<id>.output and the reason as steps.<id>.error.

Context overflow

rupu compacts proactively — summarizing older turns once the conversation reaches compactAtPercent (default 80) of the model's input limit, with room left for a full-length reply. When a provider still rejects a request as too long, rupu reads the real maximum out of the error text (Anthropic, OpenAI, Copilot, vLLM and Gemini formats are each recognized), lowers the run's input limit to it, writes a model_limits_clamped notice, compacts with a summary and retries. Deleting the oldest exchanges is the last resort.

  • An Anthropic error saying input plus max_tokens exceeds the window is treated as an output-reservation problem: the turn is retried once with a smaller max_tokens before anything is compacted.
  • An Anthropic 429 refusing a 1M-context request on an account without extra-usage billing is not retried with the beta: rupu drops to the standard 200K window for the rest of that client's life, says so, and retries once.
  • An observed limit is never written to the shared model cache — it reflects the account, not the model.

Recover on interrupt

A closed terminal, a killed process, a crash or a reboot should not throw away an hour of agent work. rupu keeps enough on disk to continue interrupted work rather than restart it.

Continue an agent run

rupu run api-reviewer --continue <agent_run_id>

rupu rebuilds the conversation from the run's transcript, drops the turn that was in flight, and tells the agent it was interrupted (so it re-checks work that may have been partially applied). The new run links back to the old transcript instead of copying it. If the run had actually finished, its recorded answer is printed without calling the model. Run it from the same project as the original; the new run needs its own run id.

A run that failed on an outcome — a refusal, a reply that kept getting cut off — has an intact conversation, so it can be continued on another model:

rupu run api-reviewer --continue <agent_run_id> --model gpt-5 --provider openai

The new model is told the earlier attempt stopped, why, and which model it is continuing on; discarded partial replies are left out. A different --model drops the agent's model-specific pins (maxTokens, contextWindowTokens, compactAtPercent and the Anthropic-specific settings) and rediscovers limits; a different --provider drops the agent's auth: mode. A run that failed for another reason (max turns, say) cannot be continued. --model and --provider also work on any plain rupu run.

Resume a workflow

rupu workflow resume <run-id> takes a failed, cancelled, rejected or paused run back and re-runs only what did not finish. Steps with a recorded result are skipped, and for_each units that succeeded are replayed from their checkpoints. For each linear step and each for_each unit without a recorded result, resume reads the latest agent attempt's transcript and picks one of three plans:

The attempt's transcriptPlanWhat runs
Stopped mid-run (killed, crashed, paused)continuedA new agent run seeded from the transcript, with a continuation note.
Had in fact finished — only its result was lostrecoveredIts final answer becomes the result; no model call.
Ended in failure, or missing / unreadablerestartedA fresh agent run from the rendered prompt.

Resume prints a summary per step before dispatching (e.g. audit: 2 continued · 1 recovered · 1 restarted), the live view marks continued and recovered steps or units with ↩ continued / ↩ recovered, and events.jsonl records each as an attempt_resumed event. Every agent attempt is logged to a per-run attempts.jsonl ledger as it starts; older runs without one are covered by deriving attempts from events.jsonl.

rupu workflow resume run_01EXAMPLE                         # continue interrupted work
rupu workflow resume run_01EXAMPLE --restart-interrupted   # start interrupted steps/units over

A run left Running by a runner that has since died is marked failed first, so the CLI alone can recover it; a run whose runner is still alive is refused.

What still restarts. parallel: sub-steps and panel: members, steps inside a loops: subgraph, and steps or units placed on a remote host (host: / distribute:) are restarted from their prompt rather than continued. The control plane's resume always continues; it has no “restart interrupted” option yet.

Model limits discovery

Every run needs its model's real input limit (for proactive compaction) and output cap (the per-request max_tokens). Per field, rupu takes the first of:

  1. the agent's contextWindowTokens / maxTokens frontmatter;
  2. a [[providers.<name>.models]] entry in config;
  3. the provider's live model list, from the cache;
  4. unknown — and the run says so.

A value of 0 counts as unset at every level. Each run writes a model_limits notice to its transcript with the values and where each came from. With an unknown input limit, compaction is off; with an unknown output cap, Anthropic requests carry 8192 and other providers get no cap (the model's own maximum).

Live lists are cached per provider (or per named account) at ~/.rupu/cache/models/<provider>.json for one hour. A run refreshes a stale or missing entry itself, bounded at 10 seconds; a failed refresh is remembered for 5 minutes so a provider outage doesn't cost every launch the timeout. Providers that expose no listing — a Gemini CLI / Code Assist login, for one — leave limits unknown unless you declare them.

rupu models list                              # CONTEXT, OUTPUT, SOURCE and FETCHED per model
rupu models list --provider anthropic-work     # a named account works too
rupu models refresh                           # re-fetch every live list; non-zero exit if none refreshed
rupu models refresh --provider openai

In the control plane, Settings → Models shows the same catalog with per-provider Refetch buttons. See Providers & Auth for where each provider's limits come from.
